# Spec Autopilot

확정된 spec 하나를 **plan → tasks → analyze → implement → 측정 · 기록 → 최종 검증**까지 한 번에 진행한다.
핵심은 피드백 루프다: 명세(인수 조건)를 기준으로 구현하고, 검증이 실패하면 사용자가 "다시 고쳐"라고 말하지 않아도 같은 작업 안에서 원인을 고치고 같은 검증을 다시 실행한다.

사람이 개입하는 지점은 아래 **체크포인트 3곳**뿐이다. 그 밖에는 멈추지 않고 진행한다.

## 시작 조건 (하나라도 어긋나면 시작하지 말고 무엇이 어긋났는지 보고)

1. 인자로 스펙 폴더 이름을 받는다 (예: `001-product-list`). 없으면 `.specify/feature.json`의 `feature_directory`를 쓴다.
2. 현재 Git 브랜치 이름 = 스펙 폴더 이름. `main`이면 즉시 중단한다.
3. `specs/<스펙>/spec.md`가 있고 `[NEEDS CLARIFICATION]`이 0개다 (Clarify 완료).
4. `CLAUDE.md`, `.specify/memory/constitution.md`, `docs/prd.md`, `docs/design-decisions.md`, `docs/spec-guide.md`를 읽었다.
5. 로컬 Supabase가 실행 중이다 (`npx supabase status`). 꺼져 있으면 `npx supabase start`를 한 번 시도하고, 실패하면 중단하고 보고한다.

## 전체 흐름

```
Plan ─▶ [체크포인트 A: plan 확인] ─▶ Tasks ─▶ Analyze 루프
     ─▶ 1단계 기준점 (구현 루프) ─▶ [체크포인트 B: 기준점 측정]
     ─▶ 3단계 개선 (구현 루프) ─▶ [체크포인트 C: 재측정]
     ─▶ 기록 (ADR · README · 측정 비교) ─▶ 최종 검증 ─▶ 완료 보고
```

## 1. Plan

- `/speckit-plan`을 실행한다. 기술 맥락은 Constitution의 기술 스택을 쓰고, 개발 환경은 Windows + PowerShell, CI는 Linux임을 반영한다.
- `research.md`에는 `docs/design-decisions.md`의 해당 케이스(K번호)에서 고려한 대안과 기각 이유를 옮긴다. 이 내용이 ADR 초안이 된다.
- 측정에 필요한 시나리오가 측정 도구(`scripts/measure.ts`)에 없으면 plan에 측정 도구 확장을 포함한다.
- 측정 대상 주소(로컬 프로덕션 빌드 `http://localhost:3000` 권장)를 하나로 정해 plan에 적는다. 전후 비교는 같은 주소로만 한다.

### 체크포인트 A: plan 확인

plan 요약을 5줄 이내로 보고하고 멈춘다. 요약에는 선택한 방식, 기각한 대안, **새로 추가할 라이브러리 목록**을 포함한다.
사용자가 승인하면 이어서 진행한다. 승인된 plan에 적힌 라이브러리만 설치할 수 있다.

## 2. Tasks

`/speckit-tasks`를 실행하되 Constitution 원칙 I의 4단계를 지킨다.

1. **기준점 구현**: 가장 단순한 방법 + 인수 조건 테스트. plan에서 고른 개선 방식은 넣지 않는다.
2. **측정**: 기준 환경에서 3회 측정, 측정한 커밋에 `<번호>-baseline` 태그
3. **개선**: plan에서 선택한 방식 적용. 설계서가 비교 측정 대상으로 남긴 대안이 있으면 먼저 적용해 비교 측정한다.
4. **재측정 · 기록**: 같은 조건 재측정, `<번호>-improved` 태그, ADR, README 갱신

각 태스크에는 **대응하는 인수 조건(spec의 SC · 인수 시나리오 번호)**과 **검증 명령**을 적는다.

## 3. Analyze 루프

1. `/speckit-analyze`를 실행한다.
2. Critical · High 이슈는 plan · tasks를 고쳐 해결한다. spec이나 Constitution을 고쳐야 해결되는 이슈면 **고치지 말고 멈춰서 보고**한다.
3. 다시 analyze를 실행한다. Critical · High가 0건이 될 때까지 반복하되, **최대 3회**. 3회 후에도 남으면 멈추고 보고한다.
4. Medium 이하는 해당 태스크 설명에 메모로 남기고 진행한다.

## 4. 구현 루프 (태스크마다)

```
구현 ─▶ 검증 명령 실행 ─▶ 통과? ─예─▶ [X] 체크 · 커밋 ─▶ 다음 태스크
                          │
                          아니오
                          ▼
               오류 읽기 → 원인 찾기 → 코드 수정 → 같은 검증 명령 재실행
               (같은 태스크에서 최대 3회. 넘으면 BLOCKED)
```

- 검증 명령: 태스크에 적힌 명령 + 항상 `npx tsc --noEmit`. 화면이나 데이터를 바꾼 태스크는 관련 E2E도 실행한다.
- **수정 · 재검증은 사용자 입력 없이 같은 작업 안에서 이어간다.** 실패 원인과 수정 내용은 진행 로그에 한 줄씩 남긴다.
- 통과하면 tasks.md를 `[X]`로 바꾸고 태스크 단위로 커밋한다: `[S1] T003 커서 페이지네이션 조회 추가`
- 3회 안에 통과하지 못하면 태스크를 `[ ]`로 두고 설명 끝에 `(BLOCKED: 원인 한 줄)`을 붙인다. 이 태스크에 의존하는 태스크는 건너뛰고, 의존하지 않는 태스크는 계속 진행한다. 단계 게이트(아래)를 통과할 수 없게 되면 멈추고 보고한다.

### 단계 게이트

각 단계가 끝나면 **전체 검증 묶음**을 실행한다: `npx tsc --noEmit` / `npm run test` / `npm run build` / `npm run test:e2e`.
전부 통과해야 다음 단계로 넘어간다. 실패하면 구현 루프와 같은 방식으로 고치고 다시 실행한다 (최대 3회).

### 통과시키려고 하면 안 되는 수정 (어기면 검증을 속인 것으로 본다)

- 실패한 테스트의 기대값 · 단언을 구현에 맞춰 바꾸기
- 테스트를 `.skip` · `.only` · 주석으로 끄기, 타임아웃만 늘려 넘기기
- `any` · `@ts-ignore` · `@ts-expect-error`로 타입 오류 숨기기
- CI 워크플로 · 린트 · 타입 검사 설정을 완화하기
- spec의 인수 조건이나 성공
