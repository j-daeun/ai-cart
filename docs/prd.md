# PRD — AI Cart (정리본)

Nov 8, 2026 · @단

**최종 목표는 AI에게 말하면 원하는 상품을 장바구니까지 손쉽게 담아주는 모바일 커머스, AI Cart다.** 1차 배포에서는 AI 없이 그 바탕이 되는 구매 흐름을 만들고, 2차 배포에서 AI 쇼핑 어시스턴트를 더한다.

**중저가 휴대폰과 느린 네트워크에서도 상품을 찾고 결제까지 막힘없이 끝낼 수 있는 모바일 커머스를 만든다.** MVP는 구매 여정 다섯 단계(목록 · 상세 · 이미지 · 결제 · AI 상담)에서 각각 핵심 문제를 풀고, 결제 단계에는 사람이 몰리는 오픈 순간까지 더한다. 셀러에게는 디자인 툴 없이 상세 이미지를 만드는 편집기를 제공한다.

## 1. 프로젝트 개요

**비전**: 기기 성능, 네트워크 상태, 결제 장애처럼 "사용자 탓이 아닌 문제" 때문에 구매를 포기하지 않는 커머스.

### 해결할 문제

| 구매 단계 | 문제 | 사용자가 겪는 일 |
| --- | --- | --- |
| 목록 | 상품 수천 개를 무한 스크롤하면 화면 요소가 쌓이고, 뒤로가기 시 위치가 사라짐 | 스크롤이 끊기고, 상세를 보고 돌아오면 처음부터 다시 찾음 |
| 상세 | 화면은 보이는데 JS 실행이 끝날 때까지 버튼이 안 눌림 | 옵션을 눌러도 반응이 없어 여러 번 누름 |
| 이미지 | 세로 수천 px짜리 상세 이미지 한 장 | 상세 설명이 한참 뒤에 뜨고, 저사양 기기는 버벅임 |
| 결제 직전 (오픈 순간) | 사람이 몰려 서버가 느려지면 사용자 새로고침과 자동 재시도가 한꺼번에 몰림 | 화면이 멈춘 줄 알고 계속 누르다 지쳐 포기 |
| 결제 | 결제 응답이 늦거나 끊기면 결과를 알 수 없고, 연타로 중복 요청 발생 | 돈이 빠졌는지 모른 채 다시 결제하거나 이탈 |
| AI 상담 | 응답을 기다리는 수 초간 무반응, 도중 취소 불가 | 기다리다 떠나거나, 질문을 바꿔도 결과가 뒤섞임 |
| 상세 이미지 제작 (셀러) | 웹사이트형 에디터는 블록을 위아래로 쌓는 방식이라 요소를 겹치거나 자유롭게 배치할 수 없고, 전문 디자인 툴은 배우기 어려움 | 상세 이미지 제작을 외주에 맡기거나, 원하는 구성을 포기 |

### 프로젝트 목적

이 PRD는 실서비스가 아닌 포트폴리오 프로젝트의 제품 정의다. 제품 목표와 별개로, 프로젝트를 통해 증명할 것은 아래 여섯 가지다.

- Next.js · TypeScript로 렌더링 경계를 설계한 근거
- 커머스 FE 핵심 흐름(목록 · 상세 · 결제)을 직접 설계한 경험
- 저사양 기준 환경에서 측정한 목표 달성 수치
- 사람이 몰리는 상황을 부하 테스트로 재현하고, 화면 쪽에서 부하를 줄인 경험
- AI 기능을 FE 역량(스트리밍 · 취소)으로 다룬 경험
- 블록을 쌓는 흐름형 에디터와 다른, 요소를 자유롭게 겹쳐 배치하는 캔버스 에디터를 설계한 경험

### 원칙

- **최선책으로 구현 · 목표 측정**: 설계서에서 고른 방식으로 바로 구현하고, 완성된 결과를 기준 환경에서 재서 목표 달성을 확인. 대안 비교 측정은 1차 배포 후 선택적으로
- **FE 몫 중심**: 서버·인프라 결정은 기능에 필요한 최소한으로
- **기준 환경 고정**: 노트북 + 크롬 CPU 보정 "저사양 모바일" 프리셋 + 느린 네트워크 프로필
- **정직한 표현**: 실사용자·실결제가 없다는 점을 먼저 밝힘

## 2. 주요 타겟

**핵심 사용자는 "출퇴근길 지하철에서 중저가 안드로이드폰으로 쇼핑하는 20\~30대"다.** 기기 성능과 네트워크가 가장 불리한 조건의 사용자를 기준으로 설계하면, 나머지 사용자는 자연스럽게 함께 좋아진다.

| 구분 | 누구 | 쇼핑 상황 | 원하는 것 | 관련 기능 |
| --- | --- | --- | --- | --- |
| 핵심 | 중저가 안드로이드폰을 쓰는 20\~30대 | 이동 중 짧은 틈에 목록을 내리고, 상세를 봤다가 돌아오기를 반복 / 지하철 구간마다 네트워크가 느려짐 | 끊기지 않는 스크롤, 돌아와도 그대로인 목록, 누르면 바로 반응하는 버튼 | 목록 무한 스크롤 · 즉시 반응하는 상세 · 긴 상세 이미지 |
| 핵심 | 같은 사용자의 오픈 순간 | 타임세일 오픈 직후 사람이 몰려 화면이 느려지고 오류가 뜸 | 지금 몇 번째인지 알고, 새로고침하지 않아도 차례가 오기 | 혼잡 시 대기 화면 |
| 핵심 | 같은 사용자의 결제 순간 | 결제 버튼을 누른 직후 네트워크가 끊기거나 응답이 늦어짐 | 돈이 빠졌는지 확실히 알고, 실수로 두 번 결제되지 않기 | 안전한 결제 |
| 핵심 | 같은 사용자의 탐색 순간 | "5만 원 이하 겨울 니트"처럼 원하는 건 있지만 필터를 하나하나 고르기 귀찮음 | 말로 물어보면 상품을 바로 보여주고, 기다리는 동안 진행 상황을 알 수 있기 | AI 쇼핑 어시스턴트 |
| 보조 | 소규모 셀러 | 디자인 툴이 익숙하지 않아 상세 이미지 제작을 외주에 맡기거나, 디자인 툴에서 만든 세로로 긴 상세 이미지를 그대로 업로드 | 디자인 툴 없이 요소를 자유롭게 배치해 상세 이미지를 직접 만들고, 따로 최적화하지 않아도 구매자 화면에서 빠르게 보이기 | 상세 이미지 편집기 · ~~긴 상세 이미지~~ |

- **우선순위에서 뺀 사용자**: 고사양 데스크톱 사용자(기본적으로 함께 좋아지므로 별도 최적화 대상 아님) / 상품 수천 개를 관리하는 대형 셀러·운영자

## 3. 핵심 기능 (MVP)

**MVP는 구매 여정 다섯 단계에 걸친 6개 기능과 셀러용 편집기 1개, 총 7개 기능이다. 결제 단계는 평상시(안전한 결제)와 혼잡한 오픈 순간(혼잡 시 대기 화면)을 함께 다룬다.** 각 기능의 구현 방향은 여러 대안을 비교한 뒤 정했다.

- **P0**: 없으면 MVP가 성립하지 않는 기능. 가장 먼저 만들고, 성공 기준을 모두 넘어야 MVP 완료
- **P1**: MVP에 포함하는 기능. P0가 끝난 뒤 착수
- **P2**: 구매 흐름을 보조하는 기능. 만드는 순서와 배포 범위는 아래 릴리스 단계를 따름

| 우선순위 | 기능 | 사용자 가치 | 구현 방향 |
| --- | --- | --- | --- |
| P0 | 상품 목록 무한 스크롤 | 끊김 없이 내려보고, 상세를 다녀와도 위치가 그대로 | 목록 가상화 + 쿼리 캐시 유지·스크롤 위치 저장 + 첫 화면 서버 렌더링 |
| P0 | 즉시 반응하는 상품 상세 | 화면이 보이면 바로 옵션·구매 버튼이 눌림 | 서버 컴포넌트 기본, 옵션·구매 영역만 클라이언트 컴포넌트 |
| P0 | 안전한 결제 | 결과를 모를 땐 "확인 중"으로 안내받고, 중복 결제가 생기지 않음 | 결제 테스트 모드 연동 / "확인 중" 상태 + 결제 조회·웹훅으로 확정 / 멱등 키 + 버튼 잠금 |
| P1 | 긴 상세 이미지 분할 표시 | 보이는 부분부터 빠르게 뜨고, 저사양 기기에서도 버벅이지 않음 | 업로드 시 분할·포맷 변환, 첫 조각 우선 로딩 + 나머지 순차 지연 로딩 |
| P1 | 혼잡 시 대기 화면 | 오픈 직후 몰려도 순번과 예상 대기 시간을 보며 기다리고, 새로고침해도 손해가 없음 | 대기 화면 + 새로고침해도 순번 유지 안내 / 지수 백오프 + 무작위 지연 + 서버 지정 대기 시간 / 짧은 간격 재요청엔 직전 결과 반환 |
| P2 | AI 쇼핑 어시스턴트 | 말로 물으면 상품 카드로 답하고, 기다리는 동안 진행 상황이 보이며, 언제든 취소 가능 / 고른 상품은 대화 안에서 바로 장바구니에 담김 | 도구 호출로 기존 검색 사용 / 단계 상태 + 스트리밍 + 상품 카드 먼저 / 요청 중단 + 부분 결과 보존 |
| P2 | 상세 이미지 편집기 (셀러) | 디자인 툴 없이 텍스트·이미지·도형을 스티커처럼 자유롭게 겹쳐 배치하고, 이미지로 저장해 상품 상세에 바로 사용 | 좌표 기반 자유 배치 캔버스 / 이동·크기·회전·겹침 순서(앞으로·뒤로) / 실행 취소·다시 실행 / 이미지로 내보낸 뒤 긴 상세 이미지 업로드·분할 과정으로 연결 |

### 릴리스 단계

**만드는 순서와 배포 범위는 우선순위가 아니라 릴리스 단계를 따른다. 1차 배포는 AI 쇼핑 어시스턴트를 뺀 6개 기능이고, 끝나면 서류에 반영해 지원을 시작한다.**

| 단계 | 기능 (만드는 순서) | 이후 |
| --- | --- | --- |
| 1차 배포 | 상품 목록 무한 스크롤 → 즉시 반응하는 상품 상세 → 안전한 결제 → 긴 상세 이미지 분할 표시 · 혼잡 시 대기 화면 → 상세 이미지 편집기 | 서류에 반영하고 지원 시작 |
| 2차 배포 | AI 쇼핑 어시스턴트 (장바구니 담기까지) | AI Cart 완성 |

AI 쇼핑 어시스턴트는 상품 검색 · 상세 · 장바구니를 도구로 불러 쓰기 때문에 마지막에 만든다.

### 바탕 기능

7개 기능이 성립하기 위해 필요한 최소 기능으로, 모두 P0와 같은 시점에 준비한다. 사용자 경험보다 "동작하면 되는" 수준으로 만든다.

- 가짜 상품 10만 개와 상품 이미지 데이터 생성 스크립트
- 목록 데이터 조회: 커서 페이지네이션
- 옵션 선택 · 장바구니 · 주문서 (최소 화면)
- 셀러용 상세 이미지 업로드 화면 + 변환 파이프라인
- AI 어시스턴트가 호출할 상품 검색 도구
- 대기열 순번 발급·조회 최소 API와 부하 테스트 스크립트 (서버 쪽 대기열 설계는 제외)
- 측정 환경: 기준 환경 프리셋 · Lighthouse CI

### 기술 스택 (잠정)

Next.js(App Router) · TypeScript / TanStack Query · Zustand / Supabase / 결제 테스트 모드 / LLM API / Vitest · Playwright / Vercel

## 4. 사용자 흐름

**사용자는 목록이나 AI 어시스턴트에서 출발해 상세로 모이고, 결제는 성공 · 확인 중 · 실패 세 갈래로 끝난다.**

&#91;embedded content: 구매 여정 · 두 입구, 결제 세 갈래\]

"확인 중"은 결과가 확정되면 완료나 실패로 이동하고, 실패에서의 재시도는 같은 멱등 키를 써서 중복 결제가 생기지 않는다. 오픈 직후처럼 혼잡할 때는 결제 전에 대기 화면을 거친다.

**셀러 흐름**: 셀러는 완성된 이미지를 직접 올리거나, 편집기에서 만든 뒤 이미지로 내보내 올릴 수 있다. 어느 경로든 같은 업로드·변환 과정을 거쳐 상품 상세에 표시된다.

## 5. 제외 범위

**MVP 7개** **기능과 그 바탕 기능 외에는 만들지 않는다.** 아래 항목은 필요해 보여도 MVP가 끝나기 전엔 손대지 않는다.

| 제외 항목 | 이유 | 이후 |
| --- | --- | --- |
| MVP 밖 개선 과제: 필터 입력 반응성 · 옵션 선택 반응 속도 · 대표 이미지 LCP·CLS · AI 응답 품질 평가 | 구매 단계별로 핵심 문제 하나씩만 고른다는 MVP 원칙 | MVP 완료 후 다음 단계 후보 (대표 이미지는 긴 상세 이미지 작업 중 일부 자연히 다룸) |
| 타임세일 시나리오 중 대기 화면 외 항목 (서버 쪽 대기열 설계 · 봇 대응 · 모니터링 · 기능 플래그) | 서버·인프라 중심이고 준비 비용이 큼 | 하지 않음 |
| 실제 결제·정산 | 사업자 등록과 결제 대행사 계약 필요 | 하지 않음, 테스트 모드만 |
| 회원가입·로그인 | 핵심 문제와 무관 | 게스트 주문으로 대체 |
| 쿠폰 · 프로모션 · 포인트 | 가격 계산은 이번에 풀 문제가 아님 | 하지 않음 |
| 리뷰 작성 · 배송 조회 · 주문 관리 | 구매 여정 밖 | 하지 않음 |
| 셀러 관리 화면 (이미지 업로드 · 편집기 외) | 상품 데이터는 시드로 대체 | 하지 않음 |
| 편집기 고급 기능 (실시간 협업 · 템플릿 마켓 · 애니메이션 · 벡터 펜 도구) | 1인 개발 MVP 범위를 넘음 | 하지 않음 |
| AI 벡터 검색 · 다른 모델 전환 · 크레딧 | 복잡도 대비 효과가 낮음 | 하지 않음 |
| 실사용자 모집 · 운영 지표 | 현실적으로 불가 | 실험실 측정으로 대체 |
| 다국어 · 데스크톱 전용 최적화 | 타겟 밖 | 하지 않음 |

## 6. 성공 기준

**1차 배포 기능 6개가 모두 아래 기준을 넘으면 1차 배포 완료, AI 쇼핑 어시스턴트까지 넘으면 프로젝트 완료다. 그 과정이 수치와 의사결정 기록으로 남으면 성공이다.** 성능 목표는 Core Web Vitals의 "좋음" 기준(LCP 2.5초 · INP 200ms · CLS 0.1 이하)을 쓰되, 저사양 기준 환경에서 닿지 못하면 측정값과 원인을 기록하고, 필요하면 대안 비교 측정으로 근거를 보강한다.

### 기능별 기준

| 우선순위 | 기능 | 성공 기준 | 측정 방법 |
| --- | --- | --- | --- |
| P0 | 상품 목록 무한 스크롤 | 상품 5,000개를 내려도 화면 요소 수가 일정 범위 유지 / 상세를 다녀오면 같은 상품이 화면에 있고 목록 재요청 0건 / 첫 화면 HTML에 상품 포함 | 성능 패널(요소 수·메모리) · E2E |
| P0 | 즉시 반응하는 상품 상세 | 상세 페이지 메인 스레드 점유 시간(TBT) 200ms 이하 · JS 전송 크기 기록 / 옵션 선택 INP 200ms 이하 | Lighthouse CI · 성능 패널 |
| P0 | 안전한 결제 | 지연 · 유실 · 중간 끊김 · 연타 · 새로고침 · 여러 탭 시나리오 전부에서 결제 1건, 최종 주문 상태 일치 (E2E 100% 통과) | Playwright + 장애 주입 |
| P1 | 긴 상세 이미지 분할 표시 | 상세 이미지 첫 조각 표시 시간 2.5초 이내 / CLS 0.1 이하 / 조각 경계에 이음매 없음 | Lighthouse · 육안 확인 |
| P1 | 혼잡 시 대기 화면 | 부하 테스트에서 재시도 시점이 한 순간에 몰리지 않고 흩어짐 (초당 요청 수 최고치 기록, 즉시 재시도와의 비교는 선택) / 새로고침해도 순번 유지 / 대기 화면에 순번과 예상 대기 시간 표시 | 부하 테스트 도구(k6 등) · E2E |
| P2 | AI 쇼핑 어시스턴트 | 응답이 끝나기 전에 상품 카드가 먼저 표시됨 (첫 카드 표시 시간 기록) / 취소 후 서버 토큰 소비 중단 / 연속 질문 시 결과 뒤섞임 0건 | 시간 계측 · E2E |
| P2 | 상세 이미지 편집기 | 요소 50개를 올려도 기준 환경에서 드래그가 끊기지 않음 / 겹침 순서 변경·실행 취소가 의도대로 동작 / 내보낸 이미지가 편집 화면과 일치 / 내보낸 이미지가 업로드·분할을 거쳐 상세에 표시 | 성능 패널(프레임) · 스크린샷 비교 테스트 · E2E |

기능과 별개로 모든 화면이 지켜야 하는 기준이다. 스펙 단계에서 각 기능의 인수 조건에 공통으로 붙는다.

| 항목 | 요구사항 |
| --- | --- |
| 성능 | 기준 환경(크롬 CPU 보정 "저사양 모바일" + 느린 네트워크)에서 측정 / 목표는 Core Web Vitals "좋음" 기준 |
| 지원 환경 | 모바일 크롬 우선, iOS 사파리는 핵심 흐름 동작만 확인 |

| 비용 | LLM 월 사용 한도 설정 / 개발 중엔 목 응답 기본 / 공개 데모엔 요청 횟수 제한 |
