# AI Cart — 스펙 S0\~S7 안내

Nov 8, 2026 · @단

**AI Cart는 스펙 8개로 나눠 만든다. 1차 배포는 S6을 뱀 7개(S0 → S1 → S2 → S3 → S4 · S5 → S7), 2차 배포는 S6 AI 쇼핑 어시스턴트다.** 각 스펙이 푸는 문제, 만드는 것, 기준점과 개선 방향, 성공 기준, 면접에서 할 이야기를 같은 형식으로 정리했다. 기준 문서는 PRD 정리본 · 문제 해결 설계서(선정안) · Constitution 1.0.0이다.

## 한눈에 보기

**만드는 순서대로 정렬했다. 스펙 번호와 만드는 순서는 다르고, S6은 번호와 관계없이 마지막에 만든다.**

| 순서 | 스펙 | 기능 | 우선순위 | 릴리스 | 먼저 필요한 것 | 예상 기간 (대략) |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | S0 `000-foundation` | 기반: 시드 데이터 · 측정 · CI · 배포 · 공통 레이아웃 | 바탕 | 1차 | 없음 | 1\~2주 |
| 2 | S1 `001-product-list` | 상품 목록 무한 스크롤 | P0 | 1차 | S0 | 2\~3주 |
| 3 | S2 `002-product-detail` | 즉시 반응하는 상품 상세 | P0 | 1차 | S1 | 2\~3주 |
| 4 | S3 `003-checkout-payment` | 장바구니 · 주문서 · 안전한 결제 | P0 | 1차 | S2 | 2\~3주 |
| 5 | S4 `004-detail-image` | 긴 상세 이미지 업로드 · 변환 · 분할 표시 | P1 | 1차 | S2 | 2\~3주 |
| 5 | S5 `005-waiting-room` | 혼잡 시 대기 화면 | P1 | 1차 | S3 | 2\~3주 |
| 6 | S7 `007-image-editor` | 상세 이미지 편집기 (셀러) | P2 | 1차 | S4 | 2\~3주 |
| 7 | S6 `006-ai-assistant` | AI 쇼핑 어시스턴트 (장바구니 담기까지) | P2 | 2차 | S1 · S2 · S3 | 2\~3주 |

S4와 S5는 서로 의존하지 않아 순서를 바꿔도 된다. 기간은 개선 단계 범위에 따라 달라지는 시작 추정값이다.

모든 기능 스펙(S1\~S7)은 같은 네 단계로 진행한다: **기준점 구현 → 측정 → 개선 → 재측정 · 기록**. 아래 각 스펙의 "기준점"은 1단계에서 가장 빨리 만드는 방식, "개선"은 설계서에서 고른 방식이다. 결제(S3)만 장애 시나리오 테스트를 먼저 쓰고 통과시키는 방식으로 진행한다.

## S0 기반 · `000-foundation`

**나머지 스펙을 만들고 잴 수 있게 해주는 밑작업이다. 구매자가 쓰는 기능은 없고, 모든 전후 비교가 이 스펙의 데이터와 측정 조건 위에서 이뤄진다.**

| 항목 | 내용 |
| --- | --- |
| 왜 필요한가 | 실사용자가 없으니 데이터를 직접 만들어야 하고, 데이터나 측정 조건이 바뀌면 이전 수치와 비교할 수 없다 |
| 만드는 것 | 시드 데이터: 상품 10만 개 · 옵션 · 재고 · 대표 이미지, 일부 상품의 긴 상세 이미지(최적화하지 않은 원본) / 측정 도구: 기준 환경 3회 측정 · 중앙값 기록 / CI: 타입 검사 · 단위 테스트 · E2E · 성능 예산 · 키 노출 검사 / 배포: `main` 본 배포 + PR 미리보기 / 공통 레이아웃: 상단 영역 · 본문 · 404 |
| 핵심 요구 | 같은 시드값이면 항상 같은 데이터 / 한 화면 안에서 같은 이미지 반복 금지(캐시 때문에 수치가 좋게 나오는 것을 막음) / 나중 스펙은 필드를 추가만 하고 기존 값은 바꾸지 않음 / 개발 서버 측정 거부 |
| 기준점 → 개선 | 해당 없음. 사용자 기능이 아니라 네 단계를 적용하지 않는다 |
| 성공 기준 | 시드 생성 10분 이내 / 두 번 생성 결과 100% 일치 / 같은 커밋 두 번 측정 시 차이 10% 이내 / 규칙을 어긴 PR 3개 모두 차단 / 레이아웃만 있는 화면이 Core Web Vitals "좋음" |
| 다른 스펙으로 넘김 | 커서 페이지네이션 → S1 / 옵션 선택 → S2 / 장바구니 · 주문서 → S3 / 업로드 · 변환 → S4 / 대기열 API · 부하 테스트 → S5 / 상품 검색 도구 → S6 |
| 면접 이야기 | 단독 이야기는 아니다. "수치를 어떤 조건에서 재나요?"라는 꼬리 질문에 답하는 근거가 된다 |

현재 상태: spec.md 작성 완료, 다음 단계는 `/speckit.clarify`.

## S1 상품 목록 무한 스크롤 · `001-product-list`

**상품 수천 개를 끊김 없이 내리고, 상세를 다녀와도 보던 자리에 그대로 돌아오게 한다.**

| 항목 | 내용 |
| --- | --- |
| 푸는 문제 | 무한 스크롤로 내릴수록 화면 요소가 쌓여 저사양 기기에서 스크롤이 끊기고 메모리가 늘어난다. 이를 가상화로 풀면 뒤로가기 시 위치가 사라지고 검색 엔진이 읽을 첫 화면이 빈다 |
| 사용자가 격는 일 | 스크롤이 끊기고, 상세를 보고 돌아오면 처음부터 다시 찾는다 |
| 만드는 것 | 상품 목록 화면 / 커서 페이지네이션 목록 조회(바탕 기능) / 상품 카드(S6에서 재사용) |
| 기준점 | 가상화 없는 단순 무한 스크롤 |
| 개선 | CSS content-visibility를 먼저 적용해 비교 측정(기각 근거용) → 목록 가상화 → 쿼리 캐시 유지 · 스크롤 위치 저장 · 첫 화면 서버 렌더링 |
| 기각한 대안 | 페이지네이션 회귀(탐색 흐름이 끊김) / 상세를 모달로 띄우기(공유 · 검색 노출이 복잡) / 목록을 브라우저 저장소에 저장(오래된 가격 · 재고 노출) |
| 성공 기준 | 상품 5,000개를 내려도 화면 요소 수가 일정 범위 유지 / 상세를 다녀오면 같은 상품이 화면에 있고 목록 재요청 0건 / 첫 화면 HTML에 상품 포함 |
| 측정 | 1천 · 5천 개 스크롤 시 요소 수 · 메모리 · 프레임을 세 방식으로 비교 / 50번째 상품 상세 후 뒤로가기 시 위치 오차와 재요청 수 |
| 범위 밖 | 필터 입력 반응성(설계서 K2, MVP 밖 개선 과제) |
| 면접 이야기 | 설계서 K1. "해결책을 넣었더니 부작용이 생겼고, 그걸 이렇게 다시 풀었다" — 꼬리 질문을 자연스럽게 이끄는 구조 |

## S2 즉시 반응하는 상품 상세 · `002-product-detail`

**상세 화면이 보이는 순간 옵션과 구매 버튼이 바로 눌리게 한다. 화면 대부분을 서버에서 그리고, 사용자가 조작하는 부분만 브라우저에서 돌리는 것이 핵심이다.**

| 항목 | 내용 |
| --- | --- |
| 푸는 문제 | 화면은 보이는데 JS 실행이 끝날 때까지 버튼이 안 눌린다. 저사양 기기일수록 빈 시간이 길다 |
| 사용자가 격는 일 | 옵션을 눌러도 반응이 없어 여러 번 누른다 |
| 만드는 것 | 상품 상세 화면(상품 정보 · 이미지 · 긴 상세 이미지 원본) / 옵션 선택(품절 옵션 표시 포함) / 구매 · 장바구니 버튼(동작은 S3) |
| 기준점 | 상세 화면 전체를 브라우저에서 그리는 방식 |
| 개선 | 서버 컴포넌트를 기본으로, 옵션 · 구매 영역만 클라이언트 컴포넌트로 나눔. 보조로 외부 스크립트 지연 로드와 CI 성능 예산을 적용(설계서 B3 · B4) |
| 성공 기준 | 상세 페이지 JS 크기와 메인 스레드 점유 시간(TBT)이 첫 구현 대비 감소 / 옵션 선택 INP 200ms 이하 |
| 측정 | Lighthouse CI · 성능 패널. 옵션 클릭 시나리오로 INP를 잰다 |
| 범위 밖 | 저사양 기기 옵션 선택 반응 속도 최적화(설계서 K4) / 대표 이미지 LCP · CLS(설계서 K6). 둘 다 MVP 밖 개선 과제 / 긴 상세 이미지 개선은 S4 |
| 면접 이야기 | 설계서 K3. "어디까지 서버에서 그리고 어디부터 브라우저에 맡길지"를 수치로 결정한 경험. PRD 목적의 "Next.js · TypeScript로 렌더링 경계를 설계한 근거"에 해당 |

## S3 장바구니 · 주문서 · 안전한 결제 · `003-checkout-payment`

**결제 응답이 늦거나 끊겨도 돈이 빠졌는지 서비스가 끝까지 확인하고, 몇 번을 눌러도 결제는 한 번만 되게 한다. S1\~S3을 마치면 목록부터 결제까지 구매 흐름이 처음으로 이어진다.**

| 항목 | 내용 |
| --- | --- |
| 푸는 문제 | 결제 대행사 응답이 늦거나 끊기면 실제로는 결제가 됐는데 화면엔 실패가 뜨거나 반응이 없다. 불안해진 사용자가 연타 · 새로고침하면 같은 주문으로 승인 요청이 두 번 이상 간다 |
| 사용자가 격는 일 | 돈이 빠졌는지 모른 채 다시 결제하거나 이탈한다 |
| 만드는 것 | 장바구니 · 주문서(최소 화면, 게스트 주문) / 결제 테스트 모드 연동 / 결제 결과 화면: 성공 · 확인 중 · 실패 |
| 진행 방식 (예외) | 정확성이 핵심이라 1단계에서 장애 시나리오 테스트를 먼저 쓰고, 그 테스트를 통과시키는 방식으로 만든다 |
| 개선 | 결과를 모를 땐 "확인 중" 상태로 두고, 화면의 결제 조회와 서버의 웹훅 두 경로로 확정 / 멱등 키로 같은 시도는 한 번만 처리 + 버튼 잠금으로 연타 자체를 줄임 |
| 핵심 판단 | "모름"을 "실패"로 처리하는 것이 가장 위험하다 / 화면 방어는 경험 개선용, 정합성은 서버의 멱등 키가 보장 / 새로고침해도 같은 키로 결과를 조회해 이어서 진행 |
| 기각한 대안 | 실패로 처리하고 재결제 유도(중복 결제) / 응답이 올 때까지 대기(이탈 · 연타) / 버튼 비활성화만(새로고침 · 다른 탭은 못 막음) |
| 성공 기준 | 지연 · 유실 · 중간 끊김 · 연타 · 새로고침 · 여러 탭 시나리오 전부에서 결제 1건, 최종 주문 상태 일치 (E2E 100% 통과, CI 자동 실행) |
| 정할 것 | 결제 대행사 (PRD 열린 질문, S3 plan에서 결정) |
| 범위 밖 | 실제 결제 · 정산 / 쿠폰 · 포인트 / 회원가입 · 로그인 / 배송 조회 · 주문 관리 |
| 면접 이야기 | 설계서 K8. 사용자가 직접 확인해야 할 일을 서비스가 대신한 사례로, 이력서 포지셔닝과 바로 연결된다 |

## S4 긴 상세 이미지 분할 표시 · `004-detail-image`

**셀러가 올린 세로로 긴 상세 이미지를 업로드 때 조각내고 변환해, 구매자 화면에서 보이는 부분부터 빠르게 띄운다. 셀러는 따로 최적화하지 않아도 된다.**

| 항목 | 내용 |
| --- | --- |
| 푸는 문제 | 세로 수천 px짜리 상세 이미지 한 장을 그대로 띄우면 다 받을 때까지 오래 걸리고, 저사양 기기는 그리는 데도 버벅인다 |
| 사용자가 격는 일 | 구매자: 상세 설명이 한참 뒤에 뜨고 스크롤이 버벅인다 / 셀러: 디자인 툴에서 만든 긴 이미지를 그대로 올릴 수밖에 없다 |
| 만드는 것 | 셀러용 상세 이미지 업로드 화면 / 업로드 시 분할 · 포맷 변환 파이프라인 / 구매자 상세 화면의 분할 표시 |
| 기준점 | S0 시드에 있는 긴 원본 이미지 한 장을 그대로 띄우는 상태 (S2에서 이미 만들어져 있음) |
| 개선 | 업로드 때 분할 · 포맷 변환 / 첫 조각 우선 로딩 + 나머지는 순서대로 지연 로딩 |
| 성공 기준 | 상세 이미지 첫 조각 표시 시간이 첫 구현 대비 단축 / CLS 0.1 이하 / 조각 경계에 이음매 없음 |
| 측정 | Lighthouse · 육안 확인 |
| 다른 스펙과의 연결 | S7 편집기에서 내보낸 이미지도 이 업로드 · 분할 과정을 그대로 탄다. 대표 이미지 최적화(설계서 K6)는 MVP 밖이지만, 변환 파이프라인을 만들면서 일부 자연히 다루게 된다 |
| 면접 이야기 | 설계서 K5. 업로드 사전 변환(설계서 C1)은 서버 쪽 처리라 전제로만 짧게 말하고, 보이는 부분부터 띄우는 화면 쪽 판단을 주인공으로 둔다 |

## S5 혼잡 시 대기 화면 · `005-waiting-room`

**타임세일 오픈 직후 사람이 몰려도, 화면이 부하를 키우지 않고 사용자를 안심시키게 한다. 서버가 버티는 방법이 아니라 서버가 힘들 때 화면이 할 일을 다룬다.**

| 항목 | 내용 |
| --- | --- |
| 푸는 문제 | 몰려서 서버가 느려지면 사용자의 새로고침 연타와 화면의 자동 재시도가 같은 박자로 몰려, 서버가 복구되자마자 다시 무너진다 |
| 사용자가 격는 일 | 화면이 멈춘 줄 알고 계속 누르다 지쳐 포기한다 |
| 만드는 것 | 대기 화면(순번 · 예상 대기 시간, 결제 전에 거침) / 대기열 순번 발급 · 조회 최소 API / 부하 테스트 스크립트 / 타임세일 상품 필드(시드에 추가만) |
| 기준점 | 오류가 나면 오류 화면만 보여주고 즉시 재시도하는 방식 |
| 개선 | 재시도 분산: 점점 늘어나는 간격(지수 백오프) + 무작위 지연 + 서버가 지정한 대기 시간 존중 / 연타 줄이기: 대기 화면 + "새로고침해도 순번이 유지돼요" 안내 / 짧은 간격 재요청엔 직전 결과 반환 |
| 핵심 판단 | 기술(재시도 분산)과 UX(연타할 이유 제거)를 함께 적용. 안내 한 줄로 트래픽을 줄이는 사례 |
| 성공 기준 | 같은 부하 조건에서 재시도 분산 후 초당 요청 수 최고치가 즉시 재시도 대비 감소 / 새로고침해도 순번 유지 / 대기 화면에 순번과 예상 대기 시간 표시 |
| 측정 | 부하 테스트 도구(k6 등)로 재시도 방식별 초당 요청 수 분포 비교 · E2E. 부하 테스트는 로컬 · 별도 환경에서 먼저 한다 |
| 범위 밖 | 서버 쪽 대기열 설계 · 봇 대응 · 모니터링 · 기능 플래그 (설계서 D1 · D2 · D6 · D7 · D8 보류) |
| 면접 이야기 | 설계서 K7. "서버를 늘리지 않고 화면 쪽에서 부하를 줄였다"는 FE 몫의 선을 분명히 긋는 것이 포인트 |

## S7 상세 이미지 편집기 · `007-image-editor`

**소규모 셀러가 디자인 툴 없이 텍스트 · 이미지 · 도형을 스티커처럼 자유롭게 겹쳐 배치해 상세 이미지를 만들고, 이미지로 내보내 바로 상품 상세에 쓴다.**

| 항목 | 내용 |
| --- | --- |
| 푸는 문제 | 웹사이트형 에디터는 블록을 위아래로 쌓는 방식이라 요소를 겹치거나 자유롭게 배치할 수 없고, 전문 디자인 툴은 배우기 어렵다 |
| 사용자가 격는 일 | 셀러가 상세 이미지 제작을 외주에 맡기거나, 원하는 구성을 포기한다 |
| 만드는 것 | 좌표 기반 자유 배치 캔버스 / 이동 · 크기 · 회전 · 겹침 순서(앞으로 · 뒤로) / 실행 취소 · 다시 실행 / 이미지로 내보내기 → S4 업로드 · 분할 과정으로 연결 |
| 기준점 → 개선 | 아직 정해지지 않았다. 설계서에 편집기 케이스가 없어서, plan 전에 대안 비교를 먼저 해야 한다 (예: 렌더링 방식, 드래그 중 상태 업데이트 방식, 실행 취소 기록 방식) |
| 성공 기준 | 요소 50개를 올려도 기준 환경에서 드래그가 끊기지 않음 / 겹침 순서 변경 · 실행 취소가 의도대로 동작 / 내보낸 이미지가 편집 화면과 일치 / 내보낸 이미지가 업로드 · 분할을 거쳐 상세에 표시 |
| 측정 | 성능 패널(프레임) · 스크린샷 비교 테스트 · E2E |
| 범위 밖 | 실시간 협업 · 템플릿 마켓 · 애니메이션 · 벡터 펜 도구 / 셀러 관리 화면(업로드 · 편집기 외) |
| 면접 이야기 | PRD 목적의 "블록을 쌓는 흐름형 에디터와 다른 자유 배치 캔버스" 경험. 기존 에디터 업무 경험과 비교해 말할 수 있다 |

## S6 AI 쇼핑 어시스턴트 · `006-ai-assistant` (2차 배포)

**"5만 원 이하 겨울 니트"처럼 말로 물으면 상품 카드로 답하고, 고른 상품을 대화 안에서 바로 장바구니에 담는다. 이 스펙이 끝나야 AI Cart가 완성된다.**

| 항목 | 내용 |
| --- | --- |
| 푸는 문제 | AI가 검색 도구를 부르고 결과를 정리해 답하기까지 수 초간 화면에 반응이 없다. 질문을 바꾸거나 떠나도 이전 요청이 계속 돌아 비용이 나가고, 늦게 온 이전 응답이 새 결과를 덮는다 |
| 사용자가 격는 일 | 필터를 하나하나 고르기 귀찮고, AI를 기다리다 떠나거나 결과가 뒤섞인다 |
| 만드는 것 | 대화 화면 / AI가 호출할 상품 검색 도구(바탕 기능) / 대화 안 상품 카드(S1 카드 재사용) → 상세(S2) · 장바구니 담기(S3) |
| 기준점 | 응답이 끝난 뒤 한 번에 표시하는 방식 |
| 개선 | AI는 의도만 해석하고 가격 · 재고는 기존 검색이 책임지는 도구 호출 구조 / "검색 중 → N개 찾음 → 정리 중" 단계 표시 + 스트리밍 + 상품 카드 먼저 / 요청 중단 + 받은 데까지 보존 |
| 기각한 대안 | 텍스트 스트리밍만(도구 호출 중엔 여전히 무반응) / 응답 끝날 때까지 입력 막기(경험 나쁨) / 끊긴 지점부터 이어 받기(서버 상태 저장 부담) |
| 성공 기준 | 첫 상품 카드 표시 시간이 "완료 후 표시" 방식 대비 단축 / 취소 후 서버 토큰 소비 중단 / 연속 질문 시 결과 뒤섞임 0건 / 장바구니 담기 기준은 S6 spec에서 정함 |
| 정할 것 | LLM 제공사와 모델 / 대화로 옵션(색상 · 사이즈) 고르는 방식 / 품절일 때 다른 옵션 권하기 여부 |
| 비용 규칙 | LLM 월 사용 한도 / 개발 중엔 목 응답 기본 / 공개 데모엔 요청 횟수 제한 |
| 범위 밖 | AI 벡터 검색 · 다른 모델 전환 · 크레딧 / AI 응답 품질 평가 세트(설계서 K10, MVP 밖 개선 과제) |
| 면접 이야기 | 설계서 K9. 취소는 "이전 요청 취소" 패턴을 AI에 그대로 적용한 것. AI를 마지막에 만든 이유(기존 기능을 도구로 쓰는 구조)도 우선순위 판단의 근거가 된다 |

1차 배포 동안 README에는 이 기능을 "개발 예정"으로 표시한다 (Constitution 원칙 V).
