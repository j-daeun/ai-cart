## K1. 무한 스크롤 목록의 성능과 탐색 흐름 (A2 + A3)

**문제 상황**: 상품 수천 개를 무한 스크롤로 내리면 화면 요소가 쌓여, 저사양 기준 환경에서 스크롤이 끊기고 메모리가 계속 늘어난다. 이를 가상화로 풀면 이번엔 상세 페이지에서 뒤로가기 했을 때 목록 위치가 사라지고, 검색 엔진이 읽을 첫 화면이 비는 부작용이 생긴다.

**원인 1. 화면 요소가 쌓여 스크롤이 끊기고 메모리가 늘어남**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 무한 스크롤 그대로 | 구현 단순 | 저사양 기기에서 끊김·메모리 증가 |
| 페이지네이션으로 회귀 | 요소 수 일정 | 탐색 흐름이 끊기고 모바일 커머스 관행과 다름 |
| CSS content-visibility | 코드 변경 최소 | 요소 자체는 남아 메모리는 그대로 |
| **목록 가상화 (선택)** | 보이는 부분만 그려 요소 수 일정 | 스크롤 복원·검색 노출을 따로 처리해야 함 (원인 2) |

**원인 2. 가상화 이후 뒤로가기 위치가 사라지고 검색 엔진이 읽을 첫 화면이 빔**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 브라우저 기본 스크롤 복원 | 별도 작업 없음 | 데이터를 다시 불러오고 가상화 목록에선 위치가 어긋남 |
| 상세를 모달로 띄우기 | 목록이 그대로 유지 | 상세 직접 진입·공유·검색 노출 처리가 복잡 |
| 목록 데이터를 브라우저 저장소에 저장 | 확실히 복원 | 저장 데이터가 크고 오래된 가격·재고를 보여줄 수 있음 |
| **쿼리 캐시 유지 + 스크롤 위치 저장 + 첫 화면 서버 렌더링 (선택)** | 다시 불러오지 않고 위치 그대로, 검색 노출도 확보 | 캐시 유지 시간 설계 필요 |

**선택과 이유**

- 저사양 기기에서 메모리까지 줄이려면 요소 자체를 줄여야 해서 가상화 선택. content-visibility는 비교 측정 대상으로 남겨 "가벼운 방법을 먼저 재보고 부족해서 바꿨다"는 근거로 씀
- 가상화가 만든 부작용은 이미 불러온 데이터를 보존하는 쿼리 캐시(TanStack Query)와 위치 저장으로 해결
- 상세를 모달로 띄우는 방식은 커머스에서 상세 페이지의 공유·검색 노출이 중요해 기각
- 바탕 작업: 목록 데이터는 커서 페이지네이션(A1)으로 불러옴

**면접 흐름**: "해결책을 넣었더니 부작용이 생겼고, 그걸 이렇게 다시 풀었다" — 꼬리 질문을 자연스럽게 이끄는 구조

**작업·검증**: 상품 1천·5천 개 스크롤 시 요소 수·메모리·프레임을 세 방식으로 비교 / 50번째 상품 상세 진입 후 뒤로가기 시 위치 오차와 재요청 수 / 첫 화면이 서버 렌더링으로 내려오는지 확인

## K7. 트래픽이 몰릴 때 화면이 할 일 (D3 + D1 축소분)

**문제 상황**: 오픈 순간 가상 동시 접속이 몰리면 서버가 지연과 오류를 돌려준다. 사용자는 새로고침을 연타하고 화면의 자동 재시도도 같은 박자로 몰려, 서버가 복구되자마자 다시 무너진다. 서버 증설이나 대기열 서버 설계는 범위 밖으로 두고, **화면 쪽에서 할 수 있는 일**에 집중한다.

**원인 1. 화면의 자동 재시도가 같은 박자로 몰림**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 즉시 재시도 | 빠른 복구 시도 | 폭주를 키움 |
| 고정 간격 재시도 | 단순 | 모두 같은 순간에 몰림 |
| 점점 늘어나는 간격(지수 백오프) | 전체 요청 수 감소 | 같은 시점에 실패한 사용자들은 같은 박자로 몰림 |
| **지수 백오프 + 무작위 지연 + 서버 지정 대기 시간 존중 (선택)** | 재시도 시점이 흩어지고, 서버가 대기 시간을 지시 | 일부 사용자는 운 나쁘게 늦게 재시도 |

**원인 2. 사람이 새로고침을 연타함**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 오류 화면만 표시 | 단순 | 화면이 멈춘 줄 알고 계속 누름 |
| 새로고침 시 경고 창 띄우기 | 이탈을 잠깐 막음 | 불안은 그대로라 무시하고 누름 |
| **대기 화면 + 새로고침해도 순번 유지 안내 (선택)** | 연타할 이유 자체를 없앰 | 순번 유지용 토큰 필요, 짧은 간격 재요청은 직전 결과 반환으로 보완 |

**선택과 이유**

- 기술(재시도 분산)과 UX(연타할 이유 제거)를 함께 적용하는 것이 핵심 판단
- "새로고침해도 손해 없다"는 안내 한 줄로 트래픽을 줄이는 사례 → 기술이 아니라 UX로 부하를 줄인 이야기
- 대기열은 순번을 발급·조회하는 최소 API로만 구현하고, 서버 쪽 대기열 설계(D1·D2)는 보류
- 오픈 페이지의 정적인 부분은 K3의 서버·클라이언트 경계 설계로 자연스럽게 확보

**FE 몫 선 긋기**: 서버가 버티는 방법이 아니라, 서버가 힘들 때 화면이 부하를 키우지 않고 사용자를 안심시키는 방법을 다룬다

**작업·검증**: 부하 테스트로 재시도 방식별 초당 요청 수 분포 비교 / 새로고침 시 순번 유지 확인 / 대기 화면의 예상 대기 시간 표시

## K8. 결제가 불확실할 때 주문 지키기 (D4 + D5)

**문제 상황**: 결제 승인 중 결제 대행사 응답이 늦거나 끊기면, 실제로는 결제가 됐는데 화면엔 실패가 뜨거나 아무 반응이 없다. 불안해진 사용자가 버튼을 연타하거나 새로고침하면 같은 주문으로 승인 요청이 두 번 이상 간다.

**원인 1. 응답이 끊겨 결제 결과를 알 수 없음**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 실패로 처리하고 다시 결제 유도 | 단순 | 이미 결제됐다면 중복 결제 |
| 응답이 올 때까지 계속 대기 | 오판 없음 | 사용자 이탈·연타 |
| 주문 내역에서 확인하라고만 안내 | 구현 간단 | 사용자가 직접 확인해야 함 |
| **"확인 중" 상태 + 결제 조회로 확정 + 웹훅으로 보완 (선택)** | 모를 땐 모른다고 안내하고 최종 결과로 확정 | 상태가 하나 늘어 화면·주문 흐름 설계가 복잡해짐 |

**원인 2. 연타·새로고침으로 같은 결제 요청이 여러 번 감**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 버튼 비활성화만 | 간단 | 새로고침·다른 탭·네트워크 재전송은 못 막음 |
| 서버에서 주문 상태로만 차단 | 확실 | 동시에 도착한 두 요청의 경쟁 처리 필요 |
| **멱등 키 + 버튼 잠금 (선택)** | 같은 시도는 몇 번 와도 한 번만 처리, 화면은 연타 자체를 줄임 | 키 생성·보관 방식 설계 필요 |

**선택과 이유**

- 결제에선 "모름"을 "실패"로 처리하는 것이 가장 위험 → 결과 불명을 별도 상태로 둠
- 화면 방어(버튼 잠금)는 경험 개선용, 정합성은 서버의 멱등 키로 보장 → 역할을 나눈 판단
- 화면(결제 조회)과 서버(웹훅) 두 경로로 확정해 한쪽이 끊겨도 복구
- 새로고침해도 같은 키로 결과를 조회해 이어서 진행 → 두 문제가 하나의 설계로 연결됨
- 사용자가 직접 확인해야 할 일을 서비스가 대신 → 이력서 포지셔닝과 연결

**작업·검증**: 결제 테스트 모드에 지연·유실·중간 끊김 주입 / 연타·새로고침·여러 탭·동시 요청 시나리오에서 결제 1건 생성과 최종 주문 상태 정합성을 E2E로 확인

## K9. AI 응답 기다림과 취소 (E2 + E3)

**문제 상황**: AI가 상품 검색 도구를 호출하고 결과를 정리해 답하기까지 수 초가 걸리고, 그동안 화면엔 반응이 없다. 기다리다 질문을 바꾸거나 화면을 떠나도 이전 요청이 계속 돌아 비용이 나가고, 늦게 온 이전 응답이 새 질문의 결과를 덮어쓴다.

**원인 1. 응답을 기다리는 수 초간 화면에 반응이 없음**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 완료 후 한 번에 표시 | 구현 단순 | 수 초간 무반응 |
| 텍스트 스트리밍만 | 글자가 바로 나옴 | 도구 호출 중엔 여전히 아무것도 안 보임 |
| 질문 전 추천 결과 미리 보여주기 | 대기 없음 | 요청과 다른 결과일 수 있음 |
| **단계 상태 표시 + 스트리밍 + 상품 카드 먼저 (선택)** | "검색 중 → N개 찾음 → 정리 중"을 보여주고 상품 카드부터 표시 | 응답을 텍스트와 도구 결과로 나눠 처리하는 구조 필요 |

**원인 2. 도중에 취소하거나 떠나도 요청이 계속 돌고, 이전 응답이 새 결과를 덮음**

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 처리 없음 | 단순 | 비용 낭비, 응답 뒤섞임 |
| 응답이 끝날 때까지 입력 막기 | 뒤섞임 원천 차단 | 사용 경험이 나쁨 |
| 끊긴 지점부터 이어 받기 | 경험이 가장 좋음 | 서버에 진행 상태를 저장해야 해 복잡도 큼 |
| **요청 중단 + 부분 결과 보존 (선택)** | 비용이 즉시 멈추고, 받은 데까지 남겨 이어서 질문 가능 | 서버까지 중단 신호가 전달되는지 확인 필요 |

**선택과 이유**

- 사용자가 원하는 건 설명이 아니라 상품 → 검색 결과가 오는 순간 카드부터 보여줌
- "첫 반응 시간"과 "첫 상품 카드 표시 시간"을 지표로 정의
- 취소는 K2(A4)의 "이전 요청 취소" 패턴을 AI에 그대로 적용 → 프로젝트 전체에 일관된 설계
- 이어 받기 방식은 서버 상태 저장 부담으로 기각
