# Feature Specification: 상품 목록 무한 스크롤

**Feature Branch**: `001-product-list`
**Spec ID**: S1
**Created**: 2026-11-26
**Status**: Draft
**기능 우선순위**: P0
**릴리스 단계**: 1차 배포 (두 번째, S0 다음)
**Input**: PRD 정리본 2·3·6·7장 / docs/spec-guide.md S1 섹션 / specs/000-foundation/spec.md

출퇴근길 중저가 안드로이드폰으로 쇼핑하는 사용자가 상품 수천 개를 끊김 없이 내려보고, 상세를 다녀와도 보던 자리에 그대로 돌아올 수 있게 한다. 무한 스크롤로 쌓인 화면 요소가 저사양 기기에서 스크롤을 끊기게 하고, 돌아올 때 목록 첫 번째로 돌아가는 문제를 푼다.

## 범위

| 포함 | 범위 밖 |
| --- | --- |
| 상품 목록 화면 | 필터 입력 반응성 (PRD 5장 "MVP 밖 개선 과제", 설계서 K2) |
| 커서 페이지네이션 목록 조회 | 검색 입력 UI (PRD 5장 제외 범위) |
| 상품 카드 | 정렬 변경 UI (PRD 5장 제외 범위) |

> **메모**: 이 스펙에서 만드는 상품 카드는 S6 AI 쇼핑 어시스턴트의 대화 화면에서 그대로 재사용된다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 상품 목록을 끊김 없이 내려보기 (필수)

사용자는 상품 목록 화면에서 아래로 스크롤하면 새 상품이 계속 나타난다. 화면에서 멀어진 상품은 화면 자원을 과도하게 점유하지 않아, 1,000개를 내렸을 때나 5,000개를 내렸을 때나 스크롤이 고르게 움직인다.

**Why this priority**: 핵심 사용자가 이동 중 짧은 틈에 상품을 훑어보는 흐름이다. 스크롤이 끊기면 탐색 자체가 불가능해진다. PRD 1장 목록 단계의 핵심 문제.

**Independent Test**: 시드 데이터에서 5,000개까지 스크롤하면서 DOM 요소 수·메모리를 측정한다.

**Acceptance Scenarios**:

1. **Given** 상품 목록 화면 첫 진입, **When** 목록 아래로 스크롤하면, **Then** 화면 가까이에서 다음 상품들이 연이어 나타난다.
2. **Given** 상품 1,000개까지 스크롤한 상태, **When** 계속 스크롤하면, **Then** 스크롤이 끊기지 않고, 렌더링된 상품 카드 수가 뷰포트에 한 번에 보이는 카드 수의 3배 이하로 유지된다.
3. **Given** 상품 5,000개까지 스크롤한 상태에서도, **Then** 렌더링된 상품 카드 수가 여전히 뷰포트 카드 수의 3배 이하로 유지되고, 메모리 사용량이 1,000개 시점 대비 크게 늘지 않는다.
4. **Given** 키보드만 쓰는 사용자, **When** 목록에서 Tab으로 이동하면, **Then** 카드 간 이동이 가능하고 현재 포커스된 카드가 화면에 보인다.
5. **Given** 상품 카드, **When** 스크린리더로 접근하면, **Then** 상품명과 가격이 읽힌다.

---

### User Story 2 — 상세를 보고 돌아와도 보던 자리 유지 (필수)

사용자가 목록에서 50번째 상품 카드를 눌러 상세 화면으로 이동했다가 뒤로가기를 누르면, 50번째 상품이 화면에 보이는 위치에 목록이 복원된다. 목록 데이터를 다시 불러오지 않는다.

**Why this priority**: 핵심 사용자가 상세를 보고 돌아오면 처음부터 다시 찾아야 하는 것이 PRD에서 정의한 핵심 문제다. 스크롤 위치 복원 없이는 무한 스크롤이 오히려 더 불편한 UI가 된다.

**Independent Test**: 50번째 상품 카드 클릭 → 상세 → 뒤로가기 E2E에서 화면에 50번째 상품이 보이고 네트워크 목록 재요청이 0건인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 목록에서 50번째 상품 카드, **When** 카드를 누르면, **Then** 그 상품의 상세 화면으로 이동한다.
2. **Given** 상세 화면, **When** 뒤로가기를 하면, **Then** 50번째 상품 카드 면적의 50% 이상이 뷰포트 안에 있는 위치로 목록이 복원된다.
3. **Given** 뒤로가기 직후, **Then** 목록 데이터 네트워크 재요청이 0건이다.
4. **Given** 뒤로가기 직후, **Then** 돌아온 카드에 키보드 포커스가 간다 (키보드 사용자).
5. **Given** 상세에 갔다가 만료 시간이 지난 뒤 돌아온 경우, **When** 목록 데이터가 만료되어 복원이 불가능하면, **Then** 첫 번째 상품부터 다시 보여주고, 목록 상단에 "시간이 지나 목록을 새로 불러왔어요" 배너(`role="status"`)가 나타난다. 배너는 사용자가 닫기 전까지 유지된다.

### User Story 3 — 첫 화면에서 상품이 바로 보임 (필수)

사용자가 상품 목록 URL에 처음 접속하면, 화면을 받는 순간부터 상품이 보인다. JS가 아직 실행되지 않은 상태에서도 첫 번째 상품들이 HTML에 포함되어 있어, 느린 네트워크에서도 첫 화면이 비어 있지 않다.

**Why this priority**: Slow 4G 환경에서 JS가 도착하기 전까지 화면이 비어 있으면 사용자가 오래 기다려야 한다. 검색 엔진도 상품 정보를 읽을 수 있어야 한다.

**Independent Test**: 프로덕션 빌드의 목록 HTML 소스에 첫 번째 상품 이름·가격이 포함되어 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 목록 URL을 처음 요청, **When** HTML이 도착하면, **Then** 첫 번째 상품들의 이름과 가격이 HTML에 포함되어 있다.
2. **Given** JS 실행 전 상태, **When** 목록을 보면, **Then** 첫 번째 상품들이 화면에 보인다.

---

### Edge Cases

- **목록 끝에 도달**: 모든 상품을 불러온 뒤, 목록 하단에 "상품을 모두 불러왔습니다" 텍스트가 고정 표시된다(`role="status"`). 끝에 도달한 뒤에도 추가 요청이 발생하지 않는다. E2E는 시드 100,000개를 끝까지 스크롤할 수 없으므로, 목록 끝 시나리오는 상품 수가 적은 조건에서 검증한다. 구체적인 E2E 설정 방법은 plan에서 정한다.
- **다음 페이지 로딩 중 네트워크가 느릴 때**: 다음 상품을 불러오는 중임을 화면에 표시한다. 이미 받은 상품은 그대로 볼 수 있다.
- **다음 페이지 로딩 중 네트워크가 끊겼을 때**: 목록 하단에 오류 메시지(`role="alert"`)와 "다시 시도" 버튼이 인라인으로 나타난다. 이미 받은 상품은 사라지지 않는다. "다시 시도"를 누르면 실패했던 커서 이후부터 다시 불러와 목록에 이어 붙이며, 상품이 중복되거나 빠지지 않는다. 자동 재시도는 하지 않는다.
- **빠른 연속 스크롤**: 사용자가 짧은 시간에 여러 페이지 분량을 빠르게 내릴 때, 같은 페이지에 대한 중복 요청이 발생하지 않는다.
- **상세에서 만료 시간 이후에 돌아왔을 때**: 목록 데이터가 만료된 경우 첫 번째 상품부터 다시 보여주고, 목록 상단에 "시간이 지나 목록을 새로 불러왔어요" 배너(`role="status"`)가 나타난다. 배너의 "안내 닫기" 버튼은 키보드로 접근·실행 가능하며, 닫기 전까지 유지된다. 만료 시간 임계값은 plan에서 정한다.
- **첫 번째 페이지 로딩 실패**: 목록 첫 화면 로드가 실패하면, 오류 안내와 다시 시도 수단을 보여준다.

## Requirements *(mandatory)*

### Functional Requirements

**목록 표시**

- **FR-001**: 상품 목록 화면은 사용자가 아래로 스크롤할 때 다음 상품들을 연속으로 불러와 목록에 이어 붙여야 한다(MUST).
- **FR-002**: 렌더링된 상품 카드 수는 언제나 뷰포트에 한 번에 보이는 카드 수의 3배 이하를 유지해야 한다(MUST). 화면 범위 밖으로 멀어진 카드가 있던 자리의 높이는 유지되어야 한다(MUST). 이 기준은 첫 구현부터 E2E로 검증하는 인수 조건이다.
- **FR-003**: 더 불러올 상품이 없으면 목록 하단에 "상품을 모두 불러왔습니다" 텍스트를 고정 표시해야 한다(MUST). 이 요소는 `role="status"`로 렌더링하여 나타날 때 스크린리더가 자동으로 읽도록 해야 한다(MUST). E2E는 이 `role="status"` 요소의 존재로 확인한다.
- **FR-004**: 다음 페이지 로딩 중에는 로딩 중임을 화면에 표시해야 한다(MUST).
- **FR-005**: 다음 페이지 로딩 오류가 발생하면 불러오기가 멈춘 자리(목록 하단)에 오류 메시지와 "다시 시도" 버튼을 인라인으로 표시해야 한다(MUST). 오류 메시지 요소는 `role="alert"`로 렌더링하여 나타날 때 스크린리더가 즉시 읽도록 해야 한다(MUST). 오류 발생 전에 불러온 상품은 사라지지 않아야 한다(MUST). "다시 시도" 버튼은 키보드로 접근하고 실행할 수 있어야 한다(MUST). 단, 오류가 나타날 때 포커스를 이 버튼으로 강제 이동하지 않는다(MUST NOT). "다시 시도"를 누르면 실패했던 커서 이후 상품부터 다시 불러오며, 상품이 중복되거나 빠지지 않아야 한다(MUST). 자동 재시도는 하지 않는다(MUST NOT).

**상품 카드**

- **FR-006**: 상품 카드는 대표 이미지·상품명·가격을 표시해야 한다(MUST).
- **FR-007**: 품절 상품 카드는 품절 상태를 시각적으로 표시해야 한다(MUST).
- **FR-008**: 상품 카드를 누르면 그 상품의 상세 화면으로 이동해야 한다(MUST).

**스크롤 위치 복원**

- **FR-009**: 상품 카드를 눌러 상세로 이동했다가 뒤로가기를 하면, 직전에 보던 상품 카드 면적의 50% 이상이 뷰포트 안에 있는 위치로 목록이 복원되어야 한다(MUST).
- **FR-010**: 위치 복원 시 목록 데이터를 다시 요청하지 않아야 한다(MUST). 만료 시간 이내에 돌아오면 위치를 복원하고, 만료 시간을 넘으면 첫 번째 상품부터 다시 보여주며 목록 상단에 상태 배너를 표시한다(MUST). 배너 문구는 "시간이 지나 목록을 새로 불러왔어요"이며 `role="status"`로 렌더링한다(MUST). 배너에는 "안내 닫기"를 접근 가능한 이름으로 가진 닫기 버튼이 있고, 키보드로 접근·실행 가능해야 한다(MUST). 만료 시간 임계값은 plan에서 정한다.
- **FR-011**: 목록에 새로 진입하는 경우(뒤로가기가 아닌 새 탐색)에는 첫 번째 상품부터 보여주어야 한다(MUST).

**첫 화면 서버 렌더링**

- **FR-012**: 목록 첫 화면(처음 보이는 상품들)은 서버에서 HTML에 포함되어 전달되어야 한다(MUST).

**접근성** (Constitution 품질 게이트)

- **FR-013**: 키보드만으로 목록 탐색(카드 간 이동)과 상세 진입이 가능해야 한다(MUST).
- **FR-014**: 모든 상품 카드는 스크린리더가 읽을 수 있는 접근 가능한 이름(상품명 포함)을 가져야 한다(MUST).
- **FR-015**: 로딩 중·오류·목록 끝 상태는 스크린리더에서도 인식할 수 있어야 한다(MUST).

### Key Entities

- **상품 목록 화면**: 상품 카드 목록과 무한 스크롤 동작. 커서 페이지네이션으로 데이터를 불러온다
- **상품 카드**: 대표 이미지·상품명·가격·품절 여부를 표시하는 최소 단위. S6에서 재사용된다
- **스크롤 위치**: 사용자가 목록에서 보던 위치. 상세에서 돌아올 때 복원에 사용된다
- **목록 데이터 캐시**: 뒤로가기 시 재요청 없이 복원하기 위해 보관하는 이전 로드 결과. 만료 여부를 가진다

## Success Criteria *(mandatory)*

### Measurable Outcomes

**PRD 6장 성공 기준 (측정 시나리오 포함)**

- **SC-001** (렌더링 카드 수 안정): 상품 1,000개·5,000개를 스크롤하는 시점 모두에서, 렌더링된 상품 카드 수 ≤ 뷰포트에 한 번에 보이는 카드 수 × 3을 E2E로 통과한다. 첫 구현부터 적용하는 인수 조건이다.
  - *측정 시나리오*: 기준 환경(저사양 모바일·Slow 4G, 프로덕션 빌드)에서 1,000개까지 스크롤 / 5,000개까지 스크롤 — 각 시점의 렌더링 카드 수·메모리·프레임 드롭 수를 3회 측정 후 중앙값 기록.

- **SC-002** (스크롤 위치 복원): 50번째 상품의 상세에 갔다가 뒤로가기를 하면 50번째 상품 카드 면적의 50% 이상이 뷰포트 안에 있고, 그 순간 목록 데이터 재요청이 0건이다.
  - *측정 시나리오*: 50번째 상품 카드 클릭 → 상세 → 뒤로가기 E2E. 판단 기준: 50번째 카드 면적의 50% 이상이 뷰포트 안에 있는지(통과/실패), 네트워크 목록 요청 수 0건(통과/실패). 추가 기록: 상세 진입 직전 scrollY와 뒤로가기 직후 scrollY의 차이(px)를 측정 기록으로 함께 남긴다(통과/실패 기준 아님, 설계서 K1 "위치 오차" 항목).

- **SC-003** (첫 화면 HTML): 목록 첫 화면 HTML에 첫 번째 상품의 이름과 가격이 포함된다.
  - *측정 시나리오*: 프로덕션 빌드에서 목록 URL HTML 소스를 직접 확인.

**Constitution 품질 게이트**

- **SC-004** (성능 목표): 기준 환경에서 목록 첫 화면 LCP 2.5초 이하, CLS 0.1 이하. 달성하지 못하면 측정값과 원인을 기록하고, 대안 비교 측정은 1차 배포 후 선택적으로 한다.

## Clarifications

### Session 2026-11-27

- Q: SC-001 "DOM 요소 수 일정 배수 이내" 판단 기준을 어떻게 명시할 것인가? → A: 렌더링된 상품 카드 수 ≤ 뷰포트에 한 번에 보이는 카드 수 × 3. 첫 구현부터 E2E로 검증하는 인수 조건으로 적용한다. FR-002·SC-001·User Story 1 Scenario 2·3에 반영.
- Q: SC-002 뒤로가기 후 "화면에 보인다"의 가시 판단 기준은? → A: 50번째 카드 면적의 50% 이상이 뷰포트 안에 있어야 함. 추가로, 상세 진입 직전 scrollY와 뒤로가기 직후 scrollY의 차이(px)를 E2E에서 측정 기록용으로 함께 남긴다(통과/실패 기준 아님, 설계서 K1 "위치 오차"). FR-009·SC-002·User Story 2 Scenario 2에 반영.
- Q: 목록 끝 도달 시 안내 형태와 E2E 검증 방식은? → A: 목록 하단에 "상품을 모두 불러왔습니다" 텍스트 고정 표시, `role="status"`로 렌더링하여 스크린리더가 자동으로 읽도록 한다. E2E는 이 `role="status"` 요소로 확인. 시드 100,000개를 끝까지 스크롤할 수 없으므로, 목록 끝 E2E 시나리오는 상품 수가 적은 조건에서 검증한다. 구체적 방법은 plan에서 정한다. FR-003·Edge Case "목록 끝에 도달"에 반영.
- Q: 로딩 오류 시 재시도 UI 위치와 접근성 요건은? → A: 목록 하단(실패 위치)에 오류 메시지(`role="alert"`) + "다시 시도" 버튼 인라인 표시. 포커스 강제 이동 없음. "다시 시도"는 키보드로 접근·실행 가능. 실패 커서 이후부터 재로드(중복·누락 없음). 자동 재시도 없음(S5 범위). FR-005·Edge Case "다음 페이지 로딩 중 네트워크가 끊겼을 때"에 반영.
- Q: 뒤로가기 시 목록 데이터 만료로 위치 복원 불가 시 안내 형태는? → A: 목록 상단에 닫기 가능한 배너(`role="status"`, "alert" 아님), 문구 "시간이 지나 목록을 새로 불러왔어요". 닫기 버튼 접근 가능한 이름 "안내 닫기", 키보드 접근·실행 가능, 사용자가 닫을 때까지 유지. 만료 시간 임계값은 plan에서 정한다. spec에는 "만료 시간 이내 복원, 초과 시 배너"로 명시. FR-010·User Story 2 Scenario 5·Edge Case "상세에서 만료 시간 이후에 돌아왔을 때"에 반영.

## Assumptions

- 상품 목록 데이터는 S0에서 생성한 시드 데이터(상품 100,000개)를 사용한다. S0에서 정의한 커서 페이지네이션 목록 조회 API를 그대로 쓴다.
- 첫 화면에 렌더링하는 상품 수·한 번에 불러올 상품 수는 plan에서 정한다.
- 스크롤 위치 복원의 "만료 기준"(얼마나 오래된 캐시를 버릴 것인지)은 plan에서 정한다.
- SC-001의 렌더링 카드 수 기준(뷰포트 카드 수 × 3 이하)은 첫 구현부터 적용하는 확정 인수 조건이다.
- 목록에서 상세로 이동하는 경로는 카드 클릭만 있다고 가정한다. 모달 방식은 제외한다(PRD 설계서 기각 대안).
- 품절 상품도 목록에 표시한다. 품절 상품 상세 진입 여부는 S2에서 정한다.
- 모바일 크롬 우선으로 만들고, iOS 사파리는 핵심 흐름(목록 탐색·상세 진입)만 동작 확인한다.
