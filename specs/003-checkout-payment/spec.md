### User Story 1 - 장바구니 담기·관리 및 바로 구매 (Priority: 필수)

구매자는 상품 상세 화면에서 두 가지 구매 경로 중 하나를 선택할 수 있다. "장바구니 담기"는 상품을 장바구니에 추가하고, "구매" 버튼은 장바구니를 거치지 않고 현재 선택한 상품·옵션·수량으로 바로 주문서를 연다. 두 경로 모두 주문서에 도달한 이후의 흐름(주문 생성·결제·결과 확인)은 동일하다. S2 상세 화면에 이미 있는 두 버튼(현재 비활성)이 이 스펙에서 실제로 동작하게 된다.

**Why this priority**: 구매 여정의 출발점이다. 두 버튼이 동작해야 주문서와 결제로 이어지는 전체 흐름이 성립한다.

**Independent Test**: 옵션 선택 → (1) 장바구니 담기 → 수량 변경 → 삭제, (2) 구매 버튼 → 주문서 항목 확인까지 각각 단독으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 옵션을 선택한 상태에서, **When** 장바구니 담기 버튼을 누르면, **Then** 해당 상품과 옵션이 장바구니에 추가된다.
2. **Given** 장바구니에 상품이 담겨 있을 때, **When** 수량 조절 버튼을 누르면, **Then** 수량이 변경되고 금액 합계가 갱신된다.
3. **Given** 장바구니에 상품이 담겨 있을 때, **When** 삭제 버튼을 누르면, **Then** 해당 항목이 장바구니에서 제거된다.
4. **Given** 장바구니가 비어 있을 때, **When** 장바구니 화면을 열면, **Then** 빈 장바구니 안내가 표시된다.
5. **Given** 사용자가 옵션을 선택한 상태에서, **When** 구매 버튼을 누르면, **Then** 선택한 상품·옵션·수량이 주문 항목으로 채워진 주문서 화면이 열리고, 장바구니 내용은 변경되지 않는다.
6. **Given** 장바구니에서 주문한 결제가 성공했을 때, **When** 결제 결과 화면을 확인하면, **Then** 주문에 포함된 항목만 장바구니에서 제거된다.

### User Story 2 - 게스트 주문서 작성 (Priority: 필수)

구매자는 회원가입이나 로그인 없이 이름·연락처·배송지를 입력해 주문서를 완성할 수 있다. 주문서는 장바구니 경로와 바로 구매 경로 모두에서 같은 화면을 사용하며, 주문 항목만 다르다.

**Why this priority**: 회원 인증 단계 없이 구매 완료까지 흐름을 단순하게 유지한다. PRD와 Constitution이 로그인·회원가입을 제외 범위로 명시했다.

**Independent Test**: 장바구니에서 주문서 진입 → 게스트 정보 입력 → 주문서 확인까지 단독으로 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 장바구니에 상품이 담겨 있을 때, **When** 주문하기 버튼을 누르면, **Then** 주문서 화면이 열린다.
2. **Given** 주문서 화면에서, **When** 필수 정보(이름, 연락처, 배송지)를 입력하면, **Then** 결제 버튼이 활성화된다.
3. **Given** 필수 정보가 누락된 상태에서, **When** 결제 버튼을 누르면, **Then** 누락된 필드에 오류 안내가 표시된다.

### User Story 3 - 결제 진행과 결과 확인 (Priority: 필수)

구매자는 주문서에서 결제를 진행하고, 결제 결과(성공 · 확인 중 · 실패)를 명확히 안내받는다.

**Why this priority**: 결제 흐름의 핵심이다. 결제 대행사 테스트 모드와 연동해 실제 카드 정보 없이 흐름을 완성한다.

**Independent Test**: 가짜 결제 대행사 어댑터를 사용해 성공·확인 중·실패 세 결과를 단독으로 시나리오 테스트할 수 있다.

**Acceptance Scenarios**:

1. **Given** 주문서 정보가 완성된 상태에서, **When** 결제를 진행하면, **Then** 결제 대행사 화면이 열린다.
2. **Given** 결제가 정상 승인됐을 때, **When** 결제 대행사 화면에서 돌아오면, **Then** 성공 화면과 주문 번호가 표시된다.
3. **Given** 결제 처리 중 응답이 끊기거나 지연돼 결과를 알 수 없을 때, **When** 결제 대행사 화면에서 돌아오면, **Then** "확인 중" 화면이 표시되고(재시도 버튼 없음), 최종 결과가 확정되면 해당 화면(성공 또는 실패)으로 전환된다.
4. **Given** 결제가 실패하거나 취소됐을 때, **When** 결제 대행사 화면에서 돌아오면, **Then** 실패 이유(예: 카드 한도 초과, 사용자 취소)를 짧게 표시한 실패 화면이 열리고, "다시 결제하기" 버튼과 "장바구니로 돌아가기" 링크가 함께 제공된다.
5. **Given** 확정 실패 화면에서, **When** "다시 결제하기" 버튼을 누르면, **Then** 같은 주문 항목으로 새 결제 시도가 시작된다.
6. **Given** "확인 중" 상태에서 일정 시간이 지나도 결과를 받지 못했을 때, **When** 화면이 여전히 "확인 중"이면, **Then** 화면 문구가 "결제 결과를 아직 확인하지 못했습니다. 결과가 확인되면 이 주문 페이지에 반영됩니다. 같은 주문으로 다시 결제하지 마세요."로 바뀌고 주문 번호와 주문 확인 링크가 표시된다. 결제 상태는 "확인 중"을 유지하며 재시도 버튼은 없다.
7. **Given** 사용자가 주문 확인 페이지(/orders/<주문번호>)에 접근할 때, **When** 아직 결과가 확정되지 않은 주문이면, **Then** 서버가 결제 상태를 최신 정보로 조회해 현재 상태를 표시한다.

### User Story 4 - 장애 상황에서 결제 정확성 보장 (Priority: 필수)

결제 중 연타·새로고침·여러 탭 등 어떤 상황에서도 같은 주문에 대한 결제는 한 번만 처리되고, 최종 주문 상태는 결제 대행사 기록과 일치한다.

**Why this priority**: 중복 결제는 사용자와 서비스 모두에게 직접적인 금전 피해를 준다. 이 스펙의 핵심 문제다. Constitution 품질 게이트 "결제 정확성"이 적용된다.

**Independent Test**: 가짜 결제 대행사 어댑터로 지연·응답 유실·중간 끊김·연타·새로고침·여러 탭 각 시나리오를 독립적으로 주입해 E2E 테스트를 실행할 수 있다.

**Acceptance Scenarios**:

1. **Given** 결제 버튼을 눌렀을 때, **When** 같은 버튼을 여러 번 연속으로 누르면, **Then** 결제 요청은 한 번만 처리된다.
2. **Given** 결제 처리 중에, **When** 사용자가 페이지를 새로고침하면, **Then** 같은 주문의 결제 상태를 이어서 확인할 수 있다.
3. **Given** 결제 처리 중에, **When** 같은 주문으로 여러 탭에서 동시에 결제를 시도하면, **Then** 결제는 한 번만 처리된다.
4. **Given** 결제 대행사 응답이 지연되거나 유실됐을 때, **When** 결제가 실제로 성공했다면, **Then** 최종적으로 성공 상태로 확정된다.
5. **Given** 결제 대행사 응답이 중간에 끊겼을 때, **When** 결과를 알 수 없는 상태이면, **Then** "확인 중" 화면이 표시되고 결과 확인이 이어 진행된다.
6. **Given** 결제가 확정 실패 후 "다시 결제하기"로 재시도해 성공했을 때, **When** 전체 결제 기록을 확인하면, **Then** 최종 결제 처리는 1건이다.
7. **Given** "확인 중" 상태의 결제 시도가 존재할 때, **When** 같은 주문으로 새 결제를 시도하면(다른 탭·직접 API 호출 포함), **Then** 새 시도가 거부되고 현재 "확인 중" 화면으로 이동한다.
8. **Given** 여러 탭에서 같은 주문의 확정 실패 후 동시에 재시도할 때, **When** 모두 "다시 결제하기"를 누르면, **Then** 결제는 한 번만 처리된다.
9. **Given** 결제 대행사 응답이 유실돼 "확인 중" 상태에서 전환 시간이 지난 후, **When** 대행사가 늦은 웹훅으로 성공을 전송하면, **Then** 주문 확인 페이지(/orders/<주문번호>)에 성공이 표시되고 최종 결제는 1건이다.

### User Story 5 - 접근성과 모바일 호환성 (Priority: 보조)

구매자는 키보드만으로 장바구니부터 결제 완료까지 모든 흐름을 진행할 수 있고, 결제 상태 변화를 스크린리더로 안내받는다. 360px 화면에서 가로 스크롤 없이 사용할 수 있다.

**Why this priority**: PRD 7장 비기능 요구사항과 Constitution 품질 게이트(접근성)를 충족하기 위한 보조 조건이다.

**Independent Test**: 키보드 탐색 테스트, 스크린리더 안내 확인, axe 자동 검사를 단독으로 실행할 수 있다.

**Acceptance Scenarios**:

1. **Given** 마우스 없이 키보드만 사용할 때, **When** 장바구니 → 주문서 → 결제 → 결과 순서로 탭 이동하면, **Then** 모든 상호작용 요소에 포커스가 닿고 동작한다.
2. **Given** 결제 상태가 변경될 때(예: 확인 중 → 성공), **When** 스크린리더가 활성화돼 있으면, **Then** 상태 변화를 음성으로 안내한다.
3. **Given** 360px 너비 화면에서, **When** 장바구니·주문서·결제 결과 화면을 열면, **Then** 가로 스크롤 없이 모든 내용이 표시된다.
4. **Given** axe 접근성 검사를 실행했을 때, **When** 각 화면을 검사하면, **Then** 위반 항목이 0건이다.

---

### Edge Cases

- 결제 대행사가 응답하기 전에 사용자가 브라우저를 닫으면? → 주문 확인 페이지(/orders/<주문번호>)로 돌아오면 서버가 최신 결제 상태를 조회해 현재 상태를 표시한다.
- 장바구니에 담긴 상품의 재고가 주문 사이에 소진되면? → 주문서 또는 결제 단계에서 재고 부족 안내를 받는다.
- 결제 완료 후 같은 성공 URL을 직접 재방문하면? → 같은 주문 결과 화면을 보여주되, 추가 결제 처리가 발생하지 않는다.
- 장바구니에 같은 상품·옵션을 두 번 담으면? → 수량이 합산되거나 중복 항목이 추가된다. 어느 쪽이든 최종 주문 금액이 정확해야 한다.
- 바로 구매 중 장바구니에 같은 상품이 담겨 있으면? → 두 목록은 독립적으로 유지된다. 바로 구매가 완료돼도 장바구니는 변경되지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 사용자는 상품 상세 화면에서 옵션을 선택하고 장바구니에 담을 수 있어야 한다. 또한 "구매" 버튼으로 장바구니를 거치지 않고 현재 선택한 상품·옵션·수량으로 바로 주문서를 열 수 있어야 하며, 이때 장바구니 내용은 변경되지 않는다.
- **FR-002**: 사용자는 장바구니에서 상품 수량을 변경하거나 항목을 삭제할 수 있어야 한다.
- **FR-003**: 사용자는 회원가입이나 로그인 없이 이름·연락처·배송지를 입력해 게스트로 주문서를 완성할 수 있어야 한다.
- **FR-004**: 시스템은 결제 대행사 테스트 모드와 연동해 실제 카드 정보 없이 결제 흐름 전체를 완수할 수 있어야 한다.
- **FR-005**: 시스템은 결제 결과를 성공·확인 중·실패 세 가지 상태로 사용자에게 안내해야 한다. 실패 화면에는 실패 이유(예: 카드 한도 초과, 사용자 취소)를 짧게 표시하고 "다시 결제하기" 버튼과 "장바구니로 돌아가기" 링크를 제공해야 한다. "확인 중" 화면에는 새 결제 시도 버튼을 제공하지 않는다.
- **FR-006**: 결제 처리 중 결과를 알 수 없는 경우, 시스템은 "실패"가 아닌 "확인 중"으로 표시하고, 최종 결과가 확정되면 해당 상태로 전환해야 한다. 화면은 결제 조회를 간격을 늘려가며 반복한다. 일정 시간(전환 기준은 plan에서 확정, 기본안 약 1분)이 지나도 결과를 받지 못하면, 상태는 "확인 중"을 유지한 채 화면 문구만 변경하고 주문 번호와 주문 확인 링크를 표시한다. 문구 변경은 role="status"로 스크린리더에 안내한다.
- **FR-007**: 사용자가 결제 버튼을 여러 번 누르거나, 새로고침하거나, 여러 탭을 열어도 같은 주문에 대한 결제는 한 번만 처리되어야 한다.
- **FR-008**: 새로고침 후에도 진행 중이던 결제의 상태를 이어서 확인할 수 있어야 한다.
- **FR-009**: 지연·응답 유실·중간 끊김·연타·새로고침·여러 탭 장애 시나리오 E2E 테스트가 CI에서 자동으로 실행되어야 한다. 장애 시나리오는 한 경로(장바구니 또는 바로 구매 중 하나)로 실행하며, 두 경로 모두에 대해서는 "주문서에 항목이 올바르게 들어오는지"만 검증한다.
- **FR-010**: 장애 시나리오 E2E 테스트는 실제 결제 대행사에 의존하지 않는 가짜 결제 대행사 어댑터로 실행되어야 한다.
- **FR-013**: 장바구니에서 결제가 성공하면, 주문에 포함된 항목만 장바구니에서 제거되어야 한다. 바로 구매로 결제한 경우 장바구니는 변경되지 않는다.
- **FR-014**: 같은 주문으로 새 결제 시도를 허용하려면, 이전 결제 시도가 모두 확정 실패 상태여야 한다. "확인 중" 또는 "성공"인 시도가 하나라도 있으면 새 시도를 거부하고, 현재 상태 화면으로 이동시켜야 한다.
- **FR-015**: 게스트 주문 확인 페이지(/orders/<주문번호>)가 있어야 한다. 이 페이지에 접근할 때마다 서버가 결제 대행사에 결제 상태를 다시 조회해 최신 상태를 표시한다. 웹훅과 서버 조회 두 경로 모두 "확인 중" → 성공 또는 확정 실패 전환을 유발할 수 있다.
- **FR-011**: 키보드만으로 장바구니 → 주문서 → 결제 → 결과 전체 흐름을 진행할 수 있어야 한다.
- **FR-012**: 결제 상태 변화(예: 확인 중 → 성공)는 role="status"로 스크린리더에 안내되어야 한다.

### Key Entities

- **장바구니(Cart)**: 사용자가 담은 상품 항목의 집합. 각 항목은 상품·옵션 조합, 수량, 단가를 포함한다.
- **주문(Order)**: 결제로 확정되는 구매 단위. 주문 번호, 주문 항목, 배송 정보, 결제 상태를 포함한다.
- **결제 상태(Payment Status)**: 성공·확인 중·실패 세 가지. "확인 중"은 결제 대행사 응답을 알 수 없을 때의 중간 상태다.
- **결제 시도(Payment Attempt)**: 하나의 주문에 결제 시도가 여러 번 있을 수 있다(주문 1 : 결제 시도 N). 각 시도는 독립된 결제 처리 단위다. 새 시도는 이전 시도가 모두 확정 실패인 경우에만 허용된다. "확인 중"이나 "성공"인 시도가 있으면 새 시도는 거부된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 지연·응답 유실·중간 끊김·연타·새로고침·여러 탭 장애 시나리오 6가지 전부에서 결제 처리는 1건이고, 최종 주문 상태가 결제 대행사 기록과 일치한다 (E2E 100% 통과).
- **SC-002**: 모든 장애 시나리오 E2E 테스트가 가짜 결제 대행사 어댑터로 CI에서 자동 실행된다.
- **SC-003**: 장바구니 → 주문서 → 결제 → 결과 전체 흐름을 키보드만으로 진행할 수 있다.
- **SC-004**: 결제 상태가 변경될 때 스크린리더로 안내된다.
- **SC-005**: 360px 너비 화면에서 장바구니·주문서·결제 결과 화면의 가로 스크롤이 발생하지 않는다.
- **SC-006**: 각 화면의 axe 접근성 검사 위반 항목이 0건이다.
- **SC-007**: 결제 결과 화면은 성공·확인 중·실패 세 가지 상태를 모두 표시할 수 있다.
- **SC-008**: 결제 대행사 응답 유실 → "확인 중" 전환 → 늦은 웹훅 성공 도착 시나리오에서, 주문 확인 페이지에 성공이 반영되고 최종 결제는 1건이다 (E2E 통과).

## Assumptions

- 사용자는 모바일 크롬을 기본 환경으로 사용하며, iOS 사파리에서는 핵심 흐름(장바구니 → 결제 완료)만 동작을 확인한다.
- 로그인·회원가입 없이 게스트 주문으로만 처리한다. 결제 결과 확인을 위한 주문 확인 페이지(/orders/<주문번호>)는 이번 스펙 범위에 포함한다. 주문 목록 조회나 배송 추적은 범위 밖이다.
- 실제 결제와 정산은 하지 않는다. 결제 대행사 테스트 모드만 사용한다.
- 결제 대행사는 S3 plan 단계에서 선정한다. 현재는 "지연·유실·끊김을 임의로 주입할 수 있는 테스트 모드를 지원하는 대행사"를 가정한다.
- 쿠폰·포인트·프로모션은 포함하지 않는다.
- 장바구니 데이터는 브라우저 세션 단위로 유지된다(서버 저장 없음). 탭을 닫거나 세션이 만료되면 초기화된다.
- 주문서 필수 입력 필드는 최소 구성(이름·연락처·배송지)으로 한다.
- S2 상세 화면의 장바구니·구매 버튼은 현재 aria-disabled 상태로, 이 스펙에서 실제 동작으로 활성화한다.
- 성능 측정(Core Web Vitals)은 Constitution 원칙 II의 기준 환경에서 프로덕션 빌드로만 한다.
- 실제 결제 대행사 테스트 모드 연동은 Vercel Preview에서 수동으로 한 번 확인하고 결과를 기록한다.

## Clarifications

### Session 2026-11-29

- Q: S2 상세 화면의 "구매" 버튼 역할은? → A: 장바구니를 거치지 않고 바로 주문서로 이동. 선택한 상품·옵션·수량이 주문서에 미리 담긴 채로 열린다. 장바구니 내용은 변경되지 않는다. 주문서 이후(주문 생성·결제·결과 확인) 로직은 단일 경로. 장애 E2E는 한 경로로만 실행하고, 두 경로 모두 "주문서 항목 정확성"만 검증. 장바구니 경로 결제 성공 시 주문 항목만 장바구니에서 비움.
- Q: 결제 확정 실패 후 사용자가 취할 수 있는 행동은? → A: "다시 결제하기" 버튼(새 결제 시도, 새 멱등 키) + "장바구니로 돌아가기" 링크. 주문 1:결제 시도 N 관계. 서버는 이전 시도 중 "확인 중"·"성공"이 있으면 새 시도 거부 후 현재 상태 화면으로 이동. "확인 중" 화면에 재시도 버튼 없음. 실패 화면에 이유 표시 + role="status". E2E 추가 시나리오: 확정 실패 → 재시도 → 성공 = 1건 / 확인 중 중 재시도 → 거부 / 여러 탭 동시 재시도 → 1건.
- Q: "확인 중" 상태에서 오랫동안 결과가 오지 않으면 어떻게 처리하나? → A: 상태는 "확인 중" 유지, 화면 문구만 변경(전환 기준 ~1분, plan 확정). 전환 문구: "결제 결과를 아직 확인하지 못했습니다. 결과가 확인되면 이 주문 페이지에 반영됩니다. 같은 주문으로 다시 결제하지 마세요." + 주문 번호 + 주문 확인 링크. 게스트 주문 확인 페이지(/orders/<주문번호>) 신설, 방문 시마다 서버가 결제 상태 재조회. 웹훅·서버 조회 두 경로 모두 최종 상태 전환 가능. 문구 전환 role="status". 재시도 버튼 없음. E2E: 응답 유실 → 전환 → 늦은 웹훅 성공 → 주문 확인 페이지 성공 표시, 결제 1건.
