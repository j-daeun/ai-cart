**Created**: 2026-11-08
**Status**: Draft (Clarify 전)
**기능 우선순위**: 바탕

> S0는 구매자용 기능이 아니다. 여기서 "사용자"는 개발자 본인과, 기록을 보고 측정을 재현하려는 리뷰어(면접관)다.
> 측정 조건과 데이터가 S1~S7 전체의 전후 비교 기준이 되므로 tasks만이 아니라 spec으로 남긴다.

## 범위

| 포함 | 다른 스펙으로 넘김 |
| --- | --- |
| 시드 데이터 (상품 · 옵션 · 재고 · 대표 이미지 · 일부 상품의 긴 상세 이미지) | 커서 페이지네이션 → S1 |
| 기준 환경 측정과 기록 형식 | 옵션 선택 → S2 / 장바구니 · 주문서 → S3 |

| 공통 레이아웃 (상단 영역 · 본문 · 404) | AI가 호출할 상품 검색 도구 → S6 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 같은 데이터로 언제든 다시 시작 (필수)

개발자는 명령 하나로 상품 10만 개와 이미지가 연결된 데이터를 만든다. 같은 시드값이면 언제 만들어도 같은 데이터가 나온다.

**Why this priority**: 모든 기능의 전후 비교는 같은 데이터 위에서 해야 성립한다. 데이터가 바뀌면 이전 측정값을 쓸 수 없다.

**Independent Test**: 빈 데이터베이스에서 두 번 생성해 결과를 비교한다.

**Acceptance Scenarios**:

1. **Given** 빈 데이터베이스, **When** 시드 명령을 실행하면, **Then** 상품 100,000개가 생기고 모든 상품에 대표 이미지가 연결된다.
2. **Given** 같은 시드값, **When** 두 번 생성하면, **Then** 상품 순서와 모든 필드 값이 같다.
3. **Given** 데이터가 이미 있는 상태, **When** 다시 실행하면, **Then** 기존 데이터를 비우고 같은 결과로 다시 만든다. 중복 상품은 없다.
4. **Given** 생성된 데이터, **When** 등록 순서 앞쪽 100개만 봐도, **Then** 품절 상품 / 일부 옵션만 품절인 상품 / 옵션 없는 상품 / 옵션이 여러 단계인 상품 / 긴 상세 이미지가 있는 상품이 모두 들어 있다.

### User Story 2 — 기준 환경 측정을 남기고 재현하기 (필수)

개발자는 화면 하나를 기준 환경에서 3회 측정하고 중앙값을 정해진 형식으로 남긴다. 리뷰어는 기록만 보고 같은 조건을 다시 만들 수 있다.

**Why this priority**: Constitution 원칙 I · II를 지키는 도구다. S1부터 모든 기능의 2단계(측정)와 4단계(재측정)가 이 도구를 쓴다.

**Independent Test**: 공통 레이아웃만 있는 화면을 측정해 기록이 형식대로 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 프로덕션 빌드, **When** 화면 경로를 지정해 측정을 실행하면, **Then** 기준 환경 조건으로 3회 측정하고 지표별 중앙값과 3회 원값을 기록한다.
2. **Given** 측정 기록, **When** 리뷰어가 열어 보면, **Then** 측정 일시 · 커밋 · 측정 대상 주소 · 브라우저 버전 · CPU 배수 · 네트워크 프로필 · 데이터 규모 · 캐시 상태가 모두 적혀 있다.
3. **Given** 개발 서버, **When** 측정을 실행하면, **Then** 측정하지 않고 프로덕션 빌드가 필요하다고 알린다.
4. **Given** 기능 스펙이 정의한 상호작용(예: 5,000개 스크롤, 옵션 클릭), **When** 그 시나리오로 측정하면, **Then** 상호작용 중 지표도 같은 형식으로 기록된다.

### User Story 3 — PR마다 품질 게이트 자동 확인 (필수)

개발자가 PR을 올리면 Constitution의 품질 게이트가 자동으로 돌고, 하나라도 어기면 병합할 수 없다.

**Why this priority**: 혼자 개발하므로 리뷰어 대신 게이트가 회귀를 잡아야 한다.

**Independent Test**: 일부러 규칙을 어긴 PR을 올려 차단되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** PR, **When** CI가 돌면, **Then** 타입 검사 · 단위 테스트 · E2E를 실행하고 하나라도 실패하면 병합을 막는다.
2. **Given** 성능 예산이 등록되지 않은 화면, **When** CI 성능 측정이 돌면, **Then** 결과만 남기고 PR을 실패시키지 않는다.
3. **Given** 성능 예산이 등록된 화면, **When** 측정값이 예산을 넘으면, **Then** PR이 실패한다.
4. **Given** 서버 전용 키가 클라이언트 산출물에 들어간 PR, **When** CI가 돌면, **Then** PR이 실패한다.

---

### User Story 4 — 올린 코드가 바로 배포 주소에서 보이기 (필수)

개발자가 `main`에 병합하면 본 배포 주소가 바뀌고, PR을 올리면 그 PR만 반영된 미리보기 주소가 생긴다.

**Why this priority**: 배포 설정 문제는 화면이 단순할 때 겪는 게 가장 싸다. PRD 완료 체크리스트도 "배포된 URL에서 기준 환경으로 동작"을 요구한다.

**Independent Test**: 레이아웃 문구 하나를 바꾼 PR을 올리고 병합해 본다.

**Acceptance Scenarios**:

1. **Given** PR, **When** 올리면, **Then** 미리보기 주소가 생기고 PR 화면에서 그 주소로 이동할 수 있다.
2. **Given** `main` 병합, **When** 배포가 끝나면, **Then** 본 배포 주소에 변경이 반영된다.
3. **Given** 배포된 화면, **When** 데이터를 불러오면, **Then** 시드 데이터가 보이고 서버 전용 키는 브라우저에서 보이지 않는다.
4. **Given** 미리보기 주소, **When** CI 성능 측정이 돌면, **Then** 그 주소를 대상으로 잰다.

---

### User Story 5 — 모든 화면이 공유하는 레이아웃 (필수)

모바일 구매자는 어느 화면에서든 같은 상단 영역을 보고, 키보드 사용자는 본문으로 바로 건너뛸 수 있다.

**Why this priority**: 모든 기능 화면이 이 위에 올라간다. 레이아웃만 있는 화면의 측정값이 모든 기능 기준점의 바닥값이 된다.

**Independent Test**: 빈 화면에서 모바일 너비 · 키보드 조작 · 측정을 확인한다.

**Acceptance Scenarios**:

1. **Given** 너비 360px, **When** 아무 화면을 열면, **Then** 상단 영역과 본문이 가로 스크롤 없이 보인다.
2. **Given** 키보드만 쓰는 사용자, **When** 첫 Tab을 누르면, **Then** "본문으로 건너뛰기"가 먼저 포커스되고, 선택하면 본문으로 이동한다.
3. **Given** 상단 영역의 모든 조작 요소, **When** 포커스하면, **Then** 포커스 표시가 보이고 스크린리더가 읽을 이름이 있다.
4. **Given** 존재하지 않는 경로, **When** 접속하면, **Then** 공통 레이아웃 안에 안내와 홈으로 가는 링크가 보인다.

---

### Edge Cases

- **이미지 재사용과 캐시**: 대표 이미지를 적은 수의 원본에서 돌려 쓰면, 한 화면에 같은 이미지가 반복돼 브라우저 캐시 덕에 측정값이 실제보다 좋게 나온다 → 한 화면 범위 안에서는 같은 이미지가 반복되지 않아야 한다 (FR-006)
- **긴 상세 이미지의 무게**: 일부러 최적화하지 않은 원본이라, 기준 환경에서 상세 화면 로딩이 크게 느려질 수 있다 → S2는 이 상태로 기준점을 재고, 이미지 개선은 S4가 맡는다
- **시드 도중 실패**: 일부만 들어간 상태로 남으면 이후 측정이 모두 오염된다 → 전부 성공하거나 처음 상태로 돌아간다
- **측정 3회 중 1회 실패**: 그 세트 전체를 버리고 다시 잰다. 성공한 2회로 중앙값을 내지 않는다
- **측정 대상이 로컬인지 배포 주소인지**: 두 결과는 서버 위치 때문에 다르다 → 기록에 측정 대상 주소를 남기고, 전후 비교는 같은 대상끼리만 한다
- **브라우저 업데이트 · CPU 재보정**: 기록에 버전과 배수가 남으므로 전후가 다른 조건이면 기록만 보고 알 수 있다
- **상품명 극단값**: 1자 이름과 매우 긴 이름이 섞여 있어 레이아웃이 깨지는지 확인할 수 있다
- **나중 스펙이 필드를 추가할 때**: 기존 필드 값과 상품 순서가 바뀌면 이전 측정값을 쓸 수 없다 → 추가만 허용 (FR-005)

## Requirements *(mandatory)*

### Functional Requirements

**시드 데이터**

- **FR-001**: 시스템은 명령 하나로 상품 100,000개를 생성해야 한다(MUST).
- **FR-002**: 같은 시드값으로 생성한 결과는 상품 순서와 모든 필드 값이 같아야 한다(MUST).
- **FR-003**: 상품마다 이름 · 가격 · 카테고리 · 속성(계절 · 소재 등) · 대표 이미지 · 옵션(0개 이상) · 옵션별 재고 · 등록 순서를 가져야 한다(MUST). 속성은 S6에서 "5만 원 이하 겨울 니트" 같은 질의가 결과를 내도록 하기 위함이다.
- **FR-004**: 데이터에는 품절 상품 · 일부 옵션만 품절 · 옵션 없음 · 다단계 옵션 · 넓은 가격대 · 상품명 길이 극단값이 섞여 있어야 하고, 각 경우가 등록 순서 앞쪽 100개 안에도 있어야 한다(MUST). 정확한 비율은 plan에서 정한다.
- **FR-005**: 이후 스펙은 필드를 추가만 할 수 있고, 기존 상품의 순서와 필드 값을 바꾸지 않아야 한다(MUST).
- **FR-006**: 대표 이미지는 최적화하지 않은 원본 형태로 Supabase Storage에 업로드하고, 목록 한 화면 범위 안에서 같은 이미지가 반복되지 않아야 한다(MUST). 시드 스크립트 재실행 시 이미 업로드된 파일은 건너뛰어야 한다(MUST).
- **FR-007**: 일부 상품은 셀러가 디자인 툴에서 만든 그대로의 세로로 긴 상세 이미지(최적화하지 않은 원본 한 장)를 가져야 한다(MUST). 긴 이미지는 적은 수의 원본을 돌려 쓰고, 이를 가진 상품이 등록 순서 앞쪽에도 있어야 한다. 원본 파일은 Supabase Storage에 업로드한다. 원본 수 · 이미지 출처(무료 라이선스 또는 생성) · 연결할 상품 수는 plan에서 정한다.
- **FR-008**: 시드 생성은 전부 성공하거나 시작 전 상태로 돌아가야 한다(MUST).
- **FR-009**: E2E 테스트는 로컬 Supabase(Docker)에서 실행하고, CI에서도 같은 방식으로 로컬 Supabase를 띄운다(MUST). 각 실행 전 초기화는 두 단계로 나뉜다: ① 시드 데이터 테이블(상품 · 옵션 · 재고 · 이미지)은 데이터가 이미 있으면 다시 넣지 않고 존재 여부만 확인한다. ② 테스트 중 바뀌는 테이블(이후 스펙에서 추가되는 장바구니 · 주문 등)은 매번 비운다. 이 두 단계가 완료된 상태를 "시드로 초기화된 상태"로 정의한다(MUST). 원격(배포 · 측정용) Supabase DB에는 E2E가 접근하지 않는다.

**측정**

- **FR-010**: 측정은 Constitution 원칙 II의 기준 환경 조건(CPU 배수 · Slow 4G · 캐시 상태)을 자동으로 적용해야 한다(MUST).
- **FR-011**: 한 번의 측정 세트는 같은 조건 3회로 이뤄지고, 지표별 중앙값과 3회 원값을 기록해야 한다(MUST).
- **FR-012**: 페이지 로드 지표(LCP · CLS · TBT · 전송된 JS 크기)와, 기능 스펙이 정의한 상호작용 중 지표(INP · 화면 요소 수 · 메모리 · 프레임)를 잴 수 있어야 한다(MUST).
- **FR-013**: 프로덕션 빌드가 아니면 측정을 거부해야 한다(MUST).
- **FR-014**: 기록에는 측정 일시 · 커밋 · 측정 대상 주소 · 브라우저 버전 · CPU 배수 · 네트워크 프로필 · 데이터 규모 · 캐시 상태가 들어가야 한다(MUST).
- **FR-015**: 기준 환경 측정값은 스펙 ID별로 `docs/measurements/<폴더명>.json`에 누적한다(MUST). JSON은 측정 도구만 추가하고 사람이 직접 수정하지 않는 원본이다. Markdown(`docs/measurements/<폴더명>.md`)은 JSON으로부터 스크립트로 자동 생성하고, 같은 화면의 두 세트를 선택해 전후 비교 표를 출력할 수 있어야 한다(MUST). Lighthouse CI 결과는 여기에 포함하지 않는다(Constitution 원칙 II).

**CI 품질 게이트**

- **FR-016**: 모든 PR에서 타입 검사 · 단위 테스트 · E2E를 실행하고, 실패하면 병합을 막아야 한다(MUST).
- **FR-017**: 화면별 성능 예산을 등록할 수 있어야 하고, 등록된 화면만 예산 초과 시 PR을 실패시켜야 한다(MUST).
- **FR-018**: 서버 전용 키가 클라이언트 산출물에 포함되면 PR을 실패시켜야 한다(MUST).

**배포**

- **FR-019**: `main` 병합 시 본 배포 주소에 자동 반영되어야 한다(MUST).
- **FR-020**: PR마다 그 PR만 반영된 미리보기 주소가 생겨야 하고, CI 성능 측정은 이 주소를 대상으로 해야 한다(MUST).
- **FR-021**: 서버 전용 키는 배포 환경 설정과 로컬 `.env.local`에만 두고 저장소에 커밋하지 않아야 한다(MUST). Supabase 서비스 키는 시드 스크립트와 서버 코드(API Route · Server Action)에서만 사용하고, 클라이언트 코드에서 읽지 않는다(MUST).

**공통 레이아웃**

- **FR-022**: 모든 화면은 상단 영역(서비스 이름 AI Cart · 홈 이동 · 장바구니 진입 자리)과 본문 영역을 공유해야 한다(MUST). "AI Cart" 텍스트는 홈(/)으로 이동하는 `<a>` 링크로 렌더링하고, accessible name은 "AI Cart"로 시작한다(예: "AI Cart 홈")(MUST). S0에서 장바구니 버튼은 `aria-disabled="true"`로 렌더링하고(포커스 가능), accessible name은 "장바구니", 시각적으로 비활성 상태임을 알 수 있도록 흐리게 표시한다(MUST). 클릭해도 아무 동작이 없다. 실제 동작과 수량 표시는 S3에서 정한다.
- **FR-023**: 360px 너비부터 가로 스크롤 없이 표시되어야 한다(MUST). 데스크톱에서는 모바일 레이아웃을 가운데 정렬로 보여주고, 데스크톱 전용 최적화는 하지 않는다.
- **FR-024**: 첫 포커스 요소는 "본문으로 건너뛰기"여야 하고, 모든 조작 요소는 포커스 표시와 접근 가능한 이름을 가져야 한다(MUST).
- **FR-025**: 존재하지 않는 경로는 공통 레이아웃 안의 안내 화면을 보여줘야 한다(MUST).

### Key Entities

- **상품**: 이름 · 가격 · 카테고리 · 속성 · 대표 이미지 · 등록 순서. 옵션을 0개 이상, 긴 상세 이미지를 0~1개 가진다
- **옵션**: 상품에 속하는 선택 항목(예: 색상 → 사이즈). 단계를 가질 수 있다
- **재고**: 옵션 조합별 수량. 0이면 품절
- **이미지**: 대표 이미지 원본과 긴 상세 이미지 원본. 여러 상품이 같은 원본을 쓸 수 있다. Supabase Storage에 업로드된 파일의 storage path와 공개 URL을 필드로 가진다
- **측정 기록**: 스펙 ID · 화면 · 시나리오 · 측정 대상 주소 · 측정 조건 · 3회 원값 · 지표별 중앙값

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 빈 상태에서 명령 한 번으로 상품 100,000개 생성이 10분 안에 끝난다.
- **SC-002**: 같은 시드값으로 두 번 생성한 결과가 100% 일치한다.
- **SC-003**: 같은 커밋에서 측정 세트를 두 번 돌렸을 때 지표별 중앙값 차이가 10% 이내다. 10%를 넘으면 그 값을 Constitution 성능 예산 허용 오차로 개정한다.
- **SC-004**: 측정 기록에서 FR-014의 여덟 항목이 하나도 빠지지 않는다.
- **SC-005**: 타입 오류 · 실패하는 테스트 · 서버 키 노출을 각각 넣은 PR 세 개가 모두 차단된다.
- **SC-006**: PR을 올린 뒤 미리보기 주소가 생기고, `main` 병합 뒤 본 배포 주소에 반영된다 (변경 1건으로 확인).
- **SC-007**: 공통 레이아웃만 있는 화면이 배포 주소 · 기준 환경에서 Core Web Vitals "좋음" 기준을 넘고, 자동 접근성 검사에서 심각 · 치명 등급 위반이 0건이다.

## Assumptions

- 측정은 개발 노트북 1대로만 한다. 노트북을 바꾸면 Constitution 개정 대상이다
- Supabase 환경은 두 가지로 나뉜다: 원격(배포 · 성능 측정용)과 로컬 Docker(E2E · CI용). 시드 스크립트는 `SUPABASE_URL` 환경 변수만 바꿔 두 환경에 모두 사용한다. 원격 DB는 시드를 한 번만 넣고, E2E가 초기화하지 않는다
- 대표 이미지는 고유 이미지 10만 장 대신 원본 이미지 묶음을 돌려 쓴다. 묶음 크기는 FR-006을 만족하는 선에서 plan에서 정한다. 원본 파일은 Supabase Storage에 업로드하고, Git 저장소에는 포함하지 않는다
- 긴 상세 이미지는 10~20장 정도의 원본을 일부 상품에 연결한다. 원본 파일은 Supabase Storage에 업로드한다. 셀러가 직접 올리는 경로와 이미지 변환 · 분할은 S4가 만든다
- 회원가입 · 로그인은 없다 (PRD 제외 범위). 장바구니는 게스트 기준이다
- 타임세일 상품의 오픈 시각 같은 필드는 S5가 FR-005 규칙에 따라 추가한다
- 배포는 무료 플랜 안에서 한다. 부하 테스트는 배포 주소가 아니라 로컬 · 별도 환경에서 먼저 한다 (PRD 리스크 대응, S5에서 다룸)
- SC-001의 10분은 시작 기준값이다. 실제로 크게 벗어나면 Clarify 단계에서 조정한다

## Clarifications

### Session 2026-11-21

- Q: 대표 이미지와 긴 상세 이미지 원본을 어디에 보관할 것인가? → A: Supabase Storage에 실제 파일로 업로드. 이유: 최적화하지 않은 원본 무게를 직접 통제해야 하고(FR-006, FR-007), S4 셀러 업로드와 같은 Storage에서 비교 측정하기 위함. Git에는 포함하지 않는다. 시드 스크립트는 이미 올라가 있는 파일을 건너뛰는 멱등 방식으로 구현한다(FR-006). 이미지 수와 출처(무료 라이선스 또는 생성)는 plan에서 결정한다.
- Q: 공통 레이아웃 헤더의 장바구니 버튼을 S0에서 어떻게 처리할 것인가? → A: 비활성화 버튼으로 렌더링. `aria-disabled="true"` + accessible name "장바구니" + 시각적 흐림 처리. 클릭 동작 없음. 이유: S3에서 버튼이 새로 추가되면 S1·S2 측정 때와 헤더 구성이 달라져 전후 비교 조건이 바뀌므로, S0에서 자리를 고정하고 S3에서 동작만 붙인다(FR-022).
- Q: 측정 기록을 어느 파일 형식으로 저장할 것인가? → A: JSON 소스 + Markdown 자동 생성(C). 파일 경로: `docs/measurements/<폴더명>.json` / `.md`. JSON은 측정 도구만 쓰는 원본, Markdown은 스크립트 자동 생성. Lighthouse CI 결과는 별도 — 기준 환경 측정값만 이 파일에 기록한다(FR-015, Constitution 원칙 II).
- Q: 시드 스크립트를 어느 방식으로 실행할 것인가? → A: 로컬 Node.js/tsx 스크립트(A). 조건: ① Supabase 환경을 원격(배포·측정용)과 로컬 Docker(E2E·CI용)로 분리. 원격 DB는 시드 1회, E2E가 초기화 안 함. ② E2E 초기화는 시드 데이터 존재 확인 + 가변 테이블 비우기. ③ 서비스 키는 시드 스크립트와 서버 코드에서만 사용, 클라이언트 코드 금지(FR-009, FR-021).
- Q: 헤더에서 "AI Cart" 텍스트와 "홈 이동"은 같은 요소인가, 별도 요소인가? → A: "AI Cart" 텍스트가 홈 링크 역할. `<a href="/">` 하나, accessible name은 "AI Cart"로 시작(예: "AI Cart 홈")(FR-022).
